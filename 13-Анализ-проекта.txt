АНАЛИЗ ПРОЕКТА ЛОКАЛЬНОЙ МОДЕЛЬЮ: ФАКТЫ, А НЕ ШАБЛОН
Комплект 3060 12 ГБ VRAM / 16 ГБ ОЗУ. Дата: 30.10.2026
================================================================================

Зачем этот файл: 12 переключает модель, 07 выбирает задачу. Здесь — как
заставить модель РАЗБИРАТЬ проект, а не выдавать общие советы. Проблема не в
модели, а в контексте и протоколе: без фактов и цитат даже сильная модель
отвечает «по шаблону».

Три части: сборщик фактов (scripts/project-brief.mjs), карточка анализа
(templates/analysis-card.md) и правила для проекта (templates/analysis-rules.md).
Дальше по кругу работает агентный контур: цикл шага — templates/agent-protocol.md,
процедуры — templates/workflows (brief/fix/test/review/refactor), память —
templates/cline_docs, проверка — templates/verify-checklist.md, измеримость —
evals/tasks.json + scripts/agent-eval.mjs. Раздел 9 — как этим пользоваться.

--------------------------------------------------------------------------------
2. ПОЧЕМУ «ПО ШАБЛОНУ»
--------------------------------------------------------------------------------

  Симптом                          Причина
  -------------------------------  --------------------------------------------
  «Добавьте тесты и обработку      модель не видела ни одного теста и ни
  ошибок»                          одной точки входа — говорит общими словами
  «В файле X используется Y»       файл не открывался, Y придуман по имени
  «Архитектура проекта …»          пересказ README, а не кода
  Ссылки на несуществующие файлы   модель достроила «типичный» проект

  Локальная 14B на 12k контекста физически не может прочитать репозиторий.
  Поэтому выигрывает не «дать больше файлов», а дать меньше, но точнее:
  карта + несколько файлов целиком + требование цитат.

  «Обучение» здесь — это процесс (контекст + протокол + проверка цитат), а не
  дообучение весов. LoRA отложен до упора в формат, см. раздел 8.


--------------------------------------------------------------------------------
3. СБОРЩИК ФАКТОВ: scripts/project-brief.mjs
--------------------------------------------------------------------------------

Детерминированный, без зависимостей, только встроенные модули Node. Ничего не
меняет и не ходит в сеть. Обходит дерево, пропуская .git, node_modules, dist,
build, out, coverage, .next, .cache, tmp, vendor, .venv, __pycache__ и т.п.

Что печатает:

  root, git (ветка, последний коммит, число изменённых файлов)
  package: имя, версия, scripts, зависимости, devDependencies
  files: сколько файлов (без шума), крупнейшие каталоги
  entry:    точки входа из package.json (main/module/bin) и по имени
  routes:   routes/, controllers/, pages/api/, api/
  db:       migrations/, *.sql, schema.prisma, models/
  tests:    __tests__/, test/, *.test.*, *.spec.*
  configs:  tsconfig, eslint, vite, webpack, jest, vitest, Dockerfile, .env.example,
            .clinerules, AGENTS.md, opencode.json
  largest:  самые крупные файлы с размером
  markers:  TODO, FIXME, any, @ts-ignore, @ts-expect-error, eslint-disable

Ограничения (чтобы не зависнуть на гигантском репозитории):

  - файл больше 512 КБ в счётчики маркеров не попадает;
  - маркеры смотрятся максимум в 4000 файлах;
  - «any» считается только в JS/TS, иначе слово ловится в тексте Python/Go.

Команды:

    node scripts/project-brief.mjs
    node scripts/project-brief.mjs --root "D:\путь\к\проекту"
    node scripts/project-brief.mjs --root . --out tmp\brief.txt
    node scripts/project-brief.mjs --json
    node scripts/project-brief.mjs --limit 10
    node scripts/project-brief.mjs --help

  --root   корень проекта (по умолчанию текущий каталог)
  --out    записать в файл (UTF-8) вместо печати
  --json   машинный вывод для скриптов
  --limit  сколько элементов в каждом списке (по умолчанию 20)

Коды выхода: 0 — готово, 2 — ошибка аргументов или нет такого каталога.
Скрипт лежит в комплекте и работает с любым каталогом через --root; копировать
его в проект не обязательно.

Пример брифа (сокращённо):

    PROJECT BRIEF — факты для анализа (не доказательство)
    root: D:\swiftmatch1bdnoutprodpart1
    git: main · a1b2c3d feat: … · изменено файлов: 2
    package: swiftmatch 2.4.0
    scripts: dev=vite · test=vitest · build=tsc && vite build
    files: 412 (без node_modules/dist/.git)
    top: src (280), scripts (18), tests (14)
    entry: src/main.tsx
    routes: src/pages/api/health.ts, src/routes/orders.ts
    db: db/migrations/0012_orders.sql
    tests: tests/orders.test.ts
    configs: tsconfig.json, vite.config.ts, .clinerules
    largest:
      src/lib/pricing.ts — 84 КБ
    markers: TODO=12 FIXME=3 any=41 @ts-ignore=2 …
    ---
    Дальше: прочитай 3-6 файлов из entry/routes/db ЦЕЛИКОМ,
    каждое утверждение подкрепи file:line. Бриф сам по себе — не факт.


--------------------------------------------------------------------------------
4. ЧТО ЧИТАТЬ: 3-6 ФАЙЛОВ, А НЕ «ВЕСЬ ПРОЕКТ»
--------------------------------------------------------------------------------

  Приоритет выбора из брифа:

    1) entry        — с чего всё начинается;
    2) routes       — что реально торчит наружу;
    3) db           — схема и миграции, если вопрос про данные;
    4) largest      — где живёт основная сложность;
    5) tests        — что уже обещано поведением;
    6) configs      — только если вопрос про сборку/правила.

  Правило: 1 вопрос — 1 проход — до 6 файлов. Если для ответа нужно больше,
  это уже многофайловый синтез: он идёт в облако (раздел 6), а не в 14B.


--------------------------------------------------------------------------------
5. ПРОТОКОЛ: ДВА ПРОХОДА
--------------------------------------------------------------------------------

ПРОХОД 1 — СБОР (локально, 14B q4 или 7B q5):

    - прогнать project-brief.mjs;
    - выбрать 3-6 файлов по приоритету выше;
    - прочитать целиком; выписать до 10 фактов с file:line и цитатой;
    - заполнить разделы «Факты», «Риски», «Не проверено» карточки.

  Факт (01.11.2026, прогон на 4-файловом проекте): номер строки локальная
  модель называет неверно. 14B на 3 файлах дала 0/3 верных ссылок (две — в
  пустую строку, одна — в другое утверждение), 7B q5 — тоже 0/3 и писала
  «строка 5» там, где строка 4; облако на том же входе — 11/11 точно.
  Отсюда правила:

    - текст и смысл цитаты от локальной модели — годятся;
    - номер строки проверять по файлу, прежде чем вписывать в карточку;
    - если вывод держится на номере строки и проверить некому — это облако.

  Что запрещено на проходе 1:

    - ссылаться на файл, который не открывался;
    - писать «вероятно», «обычно», «как правило» без пометки «догадка»;
    - предлагать рефакторинг всего проекта;
    - делать вывод по одному имени файла.

ПРОХОД 2 — СИНТЕЗ (облако, если нужен):

    - на вход идут не файлы целиком, а карточка прохода 1 (факты + цитаты);
    - облако отвечает на вопрос «что делать», опираясь на эти факты;
    - если фактов не хватает, оно возвращает список файлов, а не выдумывает.

  Карточка — это интерфейс между проходами. Без неё облако снова начнёт
  угадывать по названиям. Шаблон: templates/analysis-card.md.

  Проверка результата человеком (30 секунд):

    - открыть 2-3 cited file:line и убедиться, что строка существует;
    - найти в ответе хотя бы одно утверждение без цитаты — это и есть «шаблон»;
    - если такое есть, ответ возвращается на доработку, а не в работу.


--------------------------------------------------------------------------------
6. КОГДА ЭСКАЛИРОВАТЬ В ОБЛАКО
--------------------------------------------------------------------------------

  Локально (local / local-q5):          В облако (cloud):
  ------------------------------------  ----------------------------------------
  один вопрос, 1-3 файла               больше 6 файлов или весь репозиторий
  цитата file:line уже есть             цитаты нет и где искать — непонятно
  правка в одном файле                  деньги/Stripe, доступы и секреты
  объяснить участок кода                схема БД и миграции
  черновик теста по существующему       деплой, инфраструктура, CI
  офлайн / нет кредитов                 ревью чужого большого PR

  Это правило, а не автоматика: маршрут выбирает человек. Автоперехода
  «локальная ошиблась -> облако» нет и не планируется (см. 12, раздел 1).
  Сменить профиль: switch-ai.bat local | local-q5 | cloud.


--------------------------------------------------------------------------------
7. ДЕСЯТЬ ВОПРОСОВ ДЛЯ ПРОВЕРКИ КАЧЕСТВА
--------------------------------------------------------------------------------

Задавайте их по одному на один прогон и сверяйте ответ с кодом. Хороший ответ —
короткий, с цитатами, с явным «не проверено».

   1. Где точка входа и что происходит в первые 20 строк после старта?
   2. Какие HTTP-роуты есть на самом деле и где они объявлены?
   3. Какая таблица/модель хранит заказы и какие у неё обязательные поля?
   4. Где обрабатываются ошибки внешнего API и что видит пользователь?
   5. Какие проверки входа есть, а каких нет (цитаты обеих сторон)?
   6. Что покрыто тестами, а что только кажется покрытым?
   7. Где дублируется бизнес-правило (одно и то же в двух местах)?
   8. Какие TODO/FIXME стоят в критическом пути, а не в косметике?
   9. Что сломается, если удалить самый крупный файл из брифа?
  10. Какая одна правка даст наибольший эффект и как её проверить?

  Признак «шаблона»: ответ подходит к любому проекту. Признак факта: в ответе
  есть строка, которую можно открыть и увидеть своими глазами.


--------------------------------------------------------------------------------
8. ПРО ДООБУЧЕНИЕ (LoRA) — ПОЗЖЕ
--------------------------------------------------------------------------------

  Сейчас «обучение» = контекст + протокол + проверка. Этого достаточно: модель
  уже умеет читать файлы, ей не хватает discipline, а не весов.

  LoRA имеет смысл только когда упрётесь в формат: модель стабильно игнорирует
  карточку, путает разделы, не ставит цитаты. Тогда:

    - собрать 200-500 пар «бриф + файлы -> карточка с цитатами»;
    - учить на своём формате ответа, а не на «знании проекта»;
    - проверять на отложенных 50 примерах, а не на обучающих;
    - держать базовую модель рядом: LoRA не должна ухудшать чтение кода.

  До этого этапа LoRA — трата времени: формат ответа дешевле задать правилами
  и шаблоном, чем обучением. Подробнее — «Что доделать», раздел 3.


--------------------------------------------------------------------------------
9. КАК ВСТРОИТЬ В ПРОЕКТ
--------------------------------------------------------------------------------

  1) Скопировать блок из templates/analysis-rules.md в конец .clinerules
     ПРОЕКТА (не комплекта). Правила живут в проекте, в комплект переносится
     копия.
  2) Положить templates/analysis-card.md в проект (например, docs/analysis-card.md)
     или держать в комплекте и заполнять вручную.
  3) Проверить на одном реальном вопросе: бриф -> 3 файла -> карточка -> сверка
     двух цитат руками.
  4) Если модель снова скатывается в шаблон — сократить число файлов до 2-3,
     а не увеличивать контекст.
  5) Агентный контур кладётся рядом:
       templates/agent-protocol.md  -> блок цикла в .clinerules проекта;
       templates/workflows/*.md     -> .clinerules/workflows/ (вызов /brief.md);
       templates/cline_docs/*.md    -> cline_docs/ (Memory Bank);
       templates/verify-checklist.md -> проверка до/после правки.
     Цикл: RESTATE -> MAP -> PLAN -> ACT -> VERIFY -> REPORT; <=2 поиска,
     <=6 чтений, 1 правка на шаг. Две неудачи подряд -> стоп и облако.
  6) Измеримость: 10 задач из evals/tasks.json, бинарный pass/fail,
     запись через scripts/agent-eval.mjs. Порог — 7/10, выдумано 0,
     среднее шагов <= 6. Пока порог не взят, LoRA не нужна: правятся правила.

  .clinerules в комплекте — копия проектного. Правки делаются в проекте; в
  комплект переносится обновлённая копия, чтобы не было двух расходящихся
  оригиналов.
