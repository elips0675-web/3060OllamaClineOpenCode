⚠️ Главное предупреждение из файла (Ошибка VRAM/RAM split)

В отчете упоминается опасная ошибка в конфигурации: запуск модели 7B в качестве «альтернативы», пока запущена модель 14B.
• Для видеокарты RTX 3060 (12 ГБ VRAM): Одновременный запуск 14B и 7B приводит к жестким тормозам (GPU split).
• Для вашего ноутбука (16 ГБ RAM): Если вы запустите qwen2.5:7b (потребует ~5 ГБ) и случайно параллельно вызовите другую модель (например, для автодополнения кода в VS Code), у вас закончится вся оперативная память. Ноутбук намертво зависнет, так как системе Windows и Git Bash просто не останется RAM.
Правило: На 16 ГБ оперативной памяти одновременно в Ollama должна быть запущена только одна модель! Перед запуском новой всегда проверяйте список через ollama ps.

там будет автопереключение между локальной моделью и из облака оллама или опенкод ?

Автоматического «магического» переключения по умолчанию нет ни в самой Ollama, ни в чистом OpenCode. Ollama — это просто сервер для локальных моделей; она ничего не знает про облака. А OpenCode — это исполнитель (движок), который строго следует конфигурации из файла opencode.json.
Тем не менее, в рамках этого комплекта гибридный подход (Local + Cloud) настраивается очень чётко через явную маршрутизацию.
Вот как это устроено на практике, согласно логике вашего документа:

1. Как это работает в самом OpenCode (через opencode.json)

В OpenCode вы разделяете задачи по Агентам (Agents). В opencode.json вы прописываете разных агентов и жестко закрепляете за каждым свою модель:
• Локальный агент (для рутины): Назначается на qwen2.5-coder:14b (через локальный Ollama endpoint). Он читает код, исправляет мелкие баги в рамках одного файла.
• Облачный агент (для сложных задач): Назначается на условный Qwen3-Coder-480B или Claude 3.5 Sonnet через API-ключ (например, OpenRouter).
Переключение происходит вручную командами или через @агента в чате:
Вы пишете в терминале обычную задачу — она уходит локальной модели. Если вы видите, что задача сложная, вы принудительно переключаете контекст (в OpenCode это делается через команду /models или вызовом облачного агента).

2. Скриптовое «автопереключение» (Особая фишка комплекта)

В начале вашего файла-отчета хвалится архитектура:
«Ключевое достоинство — детерминированный выбор задачи скриптом, а не моделью...»
Это означает, что автор комплекта решил проблему автопереключения с помощью внешнего JS-скрипта (упомянутый next-task.mjs), а не встроенных функций OpenCode.
1. Скрипт парсит ваш бэклог задач (задачи с приоритетами P0–P3).
2. Скрипт применяет «Правило эскалации»:
	• Если задача касается только одного изолированного файла 👉 скрипт генерирует промпт для локальной Ollama.

  "providers": {

1. Опасная логическая ошибка: скрипт «сам перенаправляет на /cloud»

Это неверно и противоречит главному принципу комплекта.

Скрипт next-task.mjs — это парсер бэклога на CPU. Он выбирает задачу и генерирует карточку с текстом промпта. Он не отправляет запросы ни в Ollama, ни в облако. У него нет ни доступа к API моделей, ни состояния «ошиблась дважды».

Правило эскалации — это инструкция для человека, а не автоматика:

Человек видит, что задача шире одного файла, и сам запускает /next-cloud или opencode run --agent cloud-heavy.

Человек видит, что локальная модель ошиблась дважды, и сам переключается.

2. Неверная схема opencode.json для провайдеров
Предложенный JSON использует блок "providers" с "npm": "@ai-sdk/openai-compatible" и "options": { "baseURL": ... } внутри. В актуальной документации OpenCode конфигурация провайдеров устроена иначе:

Провайдеры (Ollama, OpenRouter и т.д.) обычно настраиваются через глобальный конфиг ~/.config/opencode/opencode.json или через opencode auth login, а не через блок providers внутри проектного opencode.json.

Для локальной Ollama в документации используется отдельный подход (например, указание baseURL в конфигурации модели, а не кастомный npm-пакет).

Предложенный JSON, скорее всего, не сработает или сработает частично. Правильнее показать рабочий пример, основанный на документации.

3. Устаревшая или неверная команда переключения агента
В файле сказано: «переключаете контекст… через команду /models или вызовом облачного агента». /models переключает модель для текущей сессии, но не переключает агента. Для смены агента используется /agents select <имя>. Это важное различие: агент определяет не только модель, но и набор разрешений и системный промпт.

2. УПРАВЛЕНИЕ АГЕНТАМИ ЧЕРЕЗ TUI-ИНТЕРФЕЙС OPENCODE
--------------------------------------------------------------------------------
После запуска `opencode` (или `opencode` из cloud-start.bat) используйте 
встроенные команды TUI для строгой маршрутизации задач.

2.1. Проверка доступных моделей
Введите: /models
Ожидаемый результат: в списке должны быть ollama/swiftmatch-coder-14b (или 
swiftmatch-coder-7b) и ваша облачная модель (например, deepseek/deepseek-chat).

2.2. Принудительная маршрутизация (Главный инструмент)
• /local <текст задачи> 
  → Гарантированно отправляет задачу локальному агенту (14B). 
  → Используйте для: правки одного файла, чтения структуры, объяснения кода.
  → Пример: /local почини типы в src/pages/chats.tsx

• /cloud <текст задачи>
  → Гарантированно отправляет задачу облачному агенту.
  → Используйте для: рефакторинга >1 файла, миграций БД, разбора сложных логов.
  → Пример: /cloud спроектируй миграцию БД для новой таблицы

2.3. Интеграция со скриптом выбора задач (next-task.mjs)
• /next 
  → Вызывает скрипт с флагом --local. Выдаёт узкую карточку для 3060 (только 
    пункты с точной цитатой file:line).
• /next-cloud 
  → Вызывает скрипт без флага --local. Выдаёт карточку по приоритетам бэклога 
    для облачной модели (если задача требует обзора нескольких файлов).
• /next QA-01 
  → Принудительно запрашивает конкретный пункт по ID.

2.4. Обновление конфигурации
Если вы изменили opencode.json или добавили файлы в .opencode/commands/:
Введите: /reload
(Перезапуск OpenCode не требуется, конфиг подхватывается на лету).

3. КРИТИЧЕСКИ ВАЖНОЕ ПРАВИЛО ДЛЯ WINDOWS (из 08-Куда-писать-команды.txt)
--------------------------------------------------------------------------------
Даже если вы используете Git Bash для удобного ввода ключей, все проектные 
гейты и скрипты выбора задач НАСТОЯТЕЛЬНО РЕКОМЕНДУЕТСЯ запускать через 
нативный cmd.exe (или интегрированный терминал VS Code, настроенный на 
Command Prompt).

Почему:
1. Политика выполнения Windows блокирует npm.ps1 в PowerShell.
2. Эмуляция POSIX в Git Bash может искажать пути Windows при работе скрипта 
   next-task.mjs (например, при поиске file:line в репозитории).
3. Команды проекта ДОЛЖНЫ выглядеть так:
   npm.cmd run stage:context
   npm.cmd run stage:preflight
   npm.cmd run task:next -- --local
   npx.cmd eslint src\pages\chats.tsx

Правильный рабочий цикл:
1. Запустить cloud-start.bat (загружает ключ в сессию cmd).
2. В этом же окне cmd выполнить: npm.cmd run task:next -- --local
3. Скопировать выданную карточку.
4. Вставить карточку в OpenCode (или Cline) для исполнения.
5. После зелёных гейтов: npm.cmd run stage:checkpoint

================================================================================
Итог: Никакой «магии» и автоматического переключения. Скрипт решает ЧТО делать, 
конфиг opencode.json решает ГДЕ это делать, а вы контролируете процесс через 
явные команды /local и /cloud, сохраняя приватность данных проекта.
