2. ГЛАВНЫЙ ВЫВОД
================================================================================

«Умный агент» на 3060 — это не выбор одного харнесса и не fine-tune.
Это четыре слоя:

  1) инструменты (файлы, поиск, терминал, git, БД, HTTP);
  2) модель (локальная 14B или облако);
  3) контекст (правила, примеры, память, сжатие);
  4) проверка (тесты, линт, git diff, эвалы).

У нас лучше всего закрыт слой 3 и частично 4. Слой 1 есть в Cline/OpenCode,
но не настроен под SQL и не проверен на 14B. Слой 2 — узкое место: локальная
qwen2.5-coder-16k уверенно делает одну правку в одном файле, но плохо держит
многофайловые задачи и нативные tool_calls.

Установка OpenClose или Hermes не делает 14B умнее. Она добавляет ещё один
слой правил и контекста. Поэтому сначала закрываем дешёвые шаги 1–4 у нас,
потом сравниваем харнессы на одних и тех же 10 задачах.

4. ЧТО ЕСТЬ В OPENCLOSE И HERMES, ЧЕГО НЕТ У НАС
================================================================================

OpenClose (лежит отдельно, Python 3.12+, не плагин к Cline):
  - 14 инструментов: read/write/edit/multiedit, glob/grep, bash, webfetch,
    plan, ask_user, delegate, browser_automation_dom/vision, deliver_message;
  - агенты build (полный доступ) и plan (только чтение) + субагент delegate;
  - автоматическое сжатие контекста при подходе к лимиту;
  - Skills — процедуры в markdown, которые можно запускать и ставить в cron;
  - Jobs — расписание и уведомления в Telegram/Discord;
  - права на инструменты allow/deny/ask;
  - CLI: openclose run -p "...";
  - SQLite, без облака и телеметрии.

Hermes Agent (персональный агент, отдельный):
  - память, автосоздание навыков, самоулучшение навыков, поиск по прошлым
    сессиям (FTS5);
  - субагенты и параллельные задачи;
  - cron и мессенджеры (Telegram, Discord, Slack, WhatsApp, Signal);
  - плагины и навыки как расширения, узкое ядро;
  - SOUL.md — короткая персона: отвечать по весу вопроса, без воды;
  - бюджет промпта: AGENTS.md <= 12 КБ, цепочка <= 30 КБ.

Чего из этого нет у нас:
  1) сжатия контекста (у нас жёсткий лимит 6 вызовов и 12K ctx);
  2) read-only агента-планировщика (есть read-only эвалы, но не планирование);
  3) памяти между сессиями (шаблоны есть, автоматического recall нет);
  4) навыков как процедур (workflows статические);
  5) прав/песочницы на инструменты (держится на промпте);
  6) субагентов в правилах и эвалах (в OpenCode они есть, но не используются).

При этом инструменты у Cline и OpenCode уже есть. Проблема не в их отсутствии,
а в том, что 14B плохо держит длинный цикл и нативные tool_calls.

5. SQL И ДРУГИЕ ИНСТРУМЕНТЫ
================================================================================

SQL — это три разные задачи:

  1) чтение схемы и миграций — ЕСТЬ. Агент читает schema.prisma и SQL-файлы,
     отвечает с file:line. Это проверяют E-03 и E-09.
  2) живые запросы к MySQL — НЕТ. Ни у Cline, ни у OpenCode нет встроенного
     SQL-инструмента; SQL идёт через терминал (mysql, npx prisma) или MCP.
     В комплекте MCP не настроен, а eval-скрипт read-only.
  3) изменения схемы, миграции, данные — ЗАПРЕЩЕНО без человека. Это
     риск-домен; локальная 14B не должна выполнять ALTER/DROP/UPDATE.

Предложение: свой scripts/db-read.mjs, а не MCP.
  - только SELECT, SHOW, DESCRIBE, EXPLAIN;
  - LIMIT 100 по умолчанию, таймаут 10 секунд;
  - отдельный пользователь MySQL только на чтение;
  - лог запросов;
  - тесты на запрет INSERT/UPDATE/DELETE/DDL.
Почему не MCP: меньше зависимостей, жёстче контроль, проще проверить тестами.
Запись и миграции — только облако + человек + гейты.

Карта инструментов:

  Домен                  Cline       OpenCode    Комплект
  Файлы, поиск           да          да          да (eval)
  Терминал, тесты, git   да          да          нет (read-only)
  SQL / БД               через CLI   через CLI   нет
  HTTP / браузер         через MCP   да          нет
  Память между сессиями  вручную    вручную     шаблоны
  Расписание, Telegram   нет         нет         нет (OpenClose/Hermes)
