# 3060 Ollama · Cline · OpenCode

> Offline coding-agent kit for **RTX 3060 12 GB / 16 GB RAM**: Ollama + Qwen2.5-Coder, Cline / Continue / OpenCode,
> deterministic task selection from a Markdown backlog, and a **local-vs-cloud router** (`local` → 3060, `cloud` → `/next-cloud`).

Комплект для локального ИИ-агента на одной видеокарте: без облака, без API-ключей,
с детерминированным выбором задачи. Модель ничего не выбирает сама — она получает
узкую карточку задачи (~5 КБ) и один файл.

Канонический путь репозитория: `E:\3060OllamaClineOpenCode-main`, remote
`https://github.com/elips0675-web/3060OllamaClineOpenCode`. Других рабочих копий
нет — правки, коммиты и push идут только отсюда.

## Быстрый старт

1. `02-Установить-локально.bat` — скачать и собрать модели (пункт `[1]`, при
   желании `[4]` для автодополнения и `[5]` для лёгкой 7B q5_K_M).
2. `ollama list` — проверить, что модели на месте.
3. В OpenCode: `/models` — узнать точный ID локальной сборки (обычно `ollama/<имя>:latest`).
4. (необязательно) Если нужен `/next` в OpenCode — создайте
   `.opencode/commands/next.md` по `08`, раздел 3.3. В комплект эти команды
   не входят: каталога `.opencode` здесь нет.
5. `03-Замер-скорости.bat` — убедиться, что модель целиком на GPU.
6. Из корня проекта: `"…\switch-ai.bat" status`, затем `local` (или `cloud`).
   Перед профилем Cline закройте VS Code; в OpenCode выберите модель в `/models`
   или начните новую сессию.
7. Дальше — `00-ЧИТАЙ-ПЕРВЫМ.txt` и `09-Памятка.txt`.

## Переключение «локально ↔ облако»

`switch-ai.bat` меняет модель сразу в двух инструментах: Cline (VS Code) и
OpenCode. Профили: `local` (14B q4, основной), `local7` (7B q8), `local-q5`
(7B q5_K_M — запас VRAM), `local14-hq` (14B q6, только 16 ГБ), `cloud`
(Cline — `gpt-oss:120b-cloud`, OpenCode — бесплатная облачная модель) и
`cloud-ollama`. Скрипт мержит `opencode.json` (не теряет `instructions`),
делает бэкапы и отказывается писать Cline при запущенном VS Code.

```bat
cd /d D:\swiftmatch1bdnoutprodpart1
"D:\ИИ агент\3060 16 gb\switch-ai.bat" status
"D:\ИИ агент\3060 16 gb\switch-ai.bat" local-q5
"D:\ИИ агент\3060 16 gb\switch-ai.bat" cloud --dry-run
```

Подробно — `12-Переключение-моделей.txt`. Это явное переключение человеком, а
не автопереход «локальная ошиблась → облако»: такого механизма нет и не планируется.

## Как выбирается задача

Скрипт `next-task.mjs` (источник правды — репозиторий проекта, здесь лежит снимок)
читает `Что доделать.txt`, отбрасывает закрытые, решения и блокеры, и печатает
карточку: один пункт, один файл, гейты, готовый промпт. Строка «Маршрут» печатает
решение:

- нет цитаты `file:line` → `cloud`;
- риск-домен (деньги/Stripe, доступ и секреты, схема БД и миграции, деплой и инфраструктура) → `cloud`;
- иначе → `local`, по одному файлу за подход.

Это ключевые слова, а не оценка сложности: последнее слово за человеком.
Автоматического «упало локально → ушло в облако» нет — маршрут задаётся заранее.

## Анализ проекта, а не «по шаблону»

Локальная 14B не может прочитать репозиторий, поэтому сначала собираются факты:

```
node "D:\ИИ агент\3060 16 gb\scripts\project-brief.mjs" --root .
```

Бриф (~5 КБ) печатает точки входа, роуты, миграции, тесты, конфиги, крупные
файлы и счётчики TODO/FIXME/`any`. Это карта, а не доказательство: модель обязана
прочитать 3–6 файлов целиком и на каждое утверждение дать `file:line` с цитатой.
Итог оформляется по `templates/analysis-card.md`; правила для агента лежат в
`templates/analysis-rules.md` (блок для проектного `.clinerules`). Если для
ответа нужно больше 6 файлов или вопрос про деньги/доступы/БД — это синтез,
он идёт в облако. Подробно — `13-Анализ-проекта.txt`.

Сборщик ничего не меняет, не ходит в сеть и не требует зависимостей. Есть
`--root`, `--out`, `--json`, `--limit`; коды выхода 0/2.

## Бэклог и журнал: один механизм

`Что доделать.txt` — только открытые пункты с ID (`BLK-01`), статусом и датой
проверки. `Что сделано.txt` — журнал с развёрнутыми записями. Закрытый пункт
уходит в журнал, а в бэклоге остаётся одна компактная строка ✅ со ссылкой:

```
### BLK-01 — Установить сборки комплекта     (открытый)
Статус: ⏳ (проверено 30.10.2026)

## ✅ BLK-01 — … (см. «Что сделано.txt»: …) — ЗАКРЫТО 30.10.2026   (закрытый)
```

Тело под закрытой строкой («надгробие») запрещено, а дата «ЗАКРЫТО» должна
встречаться в журнале — иначе закрытие считается «молчаливым». Всё это
проверяет один гейт:

```
npm.cmd run check:backlog
npm.cmd run backlog:close -- --id BLK-01 --ref "раздел «BLK-01»"
npm.cmd run backlog:open -- --id DOC-01 --title "Новый пункт"
```

`backlog:close` сам откажется закрывать, если даты ещё нет в «Что сделано.txt».
Правила целиком — в конце `Что доделать.txt`.

## Агентный контур: цикл, процедуры, память, эвалы

Локальная 14B умеет читать код, но «агентность» — это дисциплина цикла, а не
объём знаний. Четыре контура ниже не требуют дообучения весов: они задают
поведение и проверяются.

**1. Протокол шага** — `templates/agent-protocol.md`, блок для проектного
`.clinerules`:

```
RESTATE → MAP → PLAN → ACT → VERIFY → REPORT
≤ 2 поиска, ≤ 6 чтений, 1 правка на шаг
две неудачи подряд → стоп; > 6 файлов или деньги/доступы/БД → облако
```

Правила держатся короткими: 14B теряет длинный системный текст. Всё длинное —
в workflows. Перед первым инструментом — Confidence Check 0–10: ниже 7 —
вопрос, а не правка. Примеры правильного ответа — `templates/few-shot.md`.

**2. Workflows** — `templates/workflows/`, копируются в
`.clinerules/workflows/` проекта и вызываются как `/brief.md`, `/fix.md`:

| Файл | Когда | Выход |
|---|---|---|
| `brief.md` | незнакомый проект, «где это лежит» | карта + до 10 фактов `file:line` |
| `fix.md` | воспроизводимый баг | причина, минимальная правка, точечный тест |
| `test.md` | закрепить существующее поведение | один тест в стиле проекта |
| `review.md` | готовый diff | блокер / желательно / вопрос, каждый с цитатой |
| `refactor.md` | упростить без смены поведения | тесты до/после, один файл |
| `deep-planning.md` | > 1 файла, неясная причина, риск-домен | `implementation_plan.md` до правок |
| `eval.md` | после правки правил/промптов/модели | число pass, дельта, что чинить |

**3. Память** — `templates/cline_docs/` (Memory Bank). Копируется в
`cline_docs/` проекта; агент читает `activeContext.md` и `progress.md` в начале
задачи и обновляет в конце. Появляется непрерывность между сессиями, которой у
локальной модели нет:

```
cline_docs/projectBrief.md     что за проект, стек, границы
cline_docs/activeContext.md    текущая задача, план, следующий шаг
cline_docs/systemPatterns.md   принятые решения и почему
cline_docs/techContext.md      команды, порты, лимиты железа
cline_docs/progress.md         что сделано / сломано / не проверено
```

**4. Проверка** — `templates/verify-checklist.md`: diff, линт, типы, точечный
тест, чтение вывода целиком, честное «не проверено». Запрещено удалять тест,
глушить линтер и расширять `any`, чтобы «позеленело».

**5. Эвалы** — `evals/tasks.json`, 10 задач с бинарным критерием (pass/fail).
Правила нельзя улучшать «на глаз»: каждая правка протокола проверяется на одном
и том же наборе.

```
npm.cmd run eval:list
npm.cmd run eval:prompt -- --id E-01
npm.cmd run eval:record -- --id E-01 --pass --steps 4 --fabricated 0 --note "цитаты рабочие"
npm.cmd run eval:score -- --strict
npm.cmd run eval:live -- --root <проект>
```

Порог «агент готов»: **pass ≥ 7/10**, выдуманных файлов/полей **0**, среднее
шагов **≤ 6**. Счёт берёт последний прогон по каждой задаче; результаты лежат в
`evals/results.json`. Подробности — `evals/README.md`.

`eval:live` — автоматический read-only прогон на локальной модели: мини-агент
получает `read_file` и `search_files`, каждая цитата проверяется по файловой
системе (выдуманный путь или строка за концом файла = fail). Гоняются 7 задач
из 10: E-04/E-05 (правка файла) и E-06 (git diff) требуют инструментов,
которых у скрипта нет. Это быстрый базовый срез, а не замена ручному прогону.

Срез 31.10.2026 (`evals/live-2026-10-31-full2.json`): **7/7 pass**, среднее
4.1 шага, выдумано 0; E-07 впервые нашёл реальные дубли (`MAX_TEXT`,
`MAX_LINES`, `MAX_RETRIES`), но ответ обрывается и теряет второй экземпляр.
Это read-only кусок набора: E-04/E-05/E-06 и ручной прогон AGT-02 в Cline
им не покрыты, поэтому порог 7/10 по всем десяти задачам пока не подтверждён.

Порядок работы: сначала AGT-02 (живой базовый балл), потом правки правил по
фактам провалов, и только если ломается именно **формат** — думать про LoRA.
Для локальной 14B это дешевле и быстрее, чем дообучение.

Если в проекте `.clinerules` — каталог (`00-role.md`, `10-gates.md`, …), цикл
кладётся отдельным файлом `40-agent-cycle.md` со ссылками на существующие
правила, а workflows — в `.clinerules/workflows/`. Переписывать действующие
правила не нужно: приоритет у `AGENTS.md` проекта.

## Снимок скрипта и тесты

`scripts/next-task.mjs` — снимок проектного селектора задач. В самом проекте
его заменил `stage:context.mjs`, поэтому копия живёт самостоятельной жизнью:
читает бэклог рядом с собой, поддерживает и заголовки `### ID — …`, и строки
таблиц с колонкой `ID` (`| P1-08 | … |`). Правки делаются здесь, в проект
ничего не переносится: форматы разошлись. Скрипт читает бэклог рядом с собой; здешний
`Что доделать.txt` теперь в формате проекта (`### BLK-01 — …` + «Статус: ⏳
(проверено ДД.ММ.ГГГГ)»), поэтому `--list` и `--id` работают на нём напрямую:

```
node scripts/next-task.mjs --list
node scripts/next-task.mjs --route
node scripts/next-task.mjs --local
node scripts/next-task.mjs --id AI-02 --route
```

Тесты (54 у селектора + 22 у переключателя + 19 у сборщика + 19 у бэклога +
23 у эвалов + 52 у живого прогона + 18 у установщика = 207) запускаются здесь же:

```
npm.cmd install
npm.cmd run test:next
npm.cmd run test:ai
npm.cmd run test:brief
npm.cmd run test:backlog
npm.cmd run test:eval
npm.cmd run test:live
npm.cmd run test:init
npm.cmd run test
```

Тесты переключателя проверяют профили, точный ID модели, мерж `opencode.json`
(`instructions` и чужие ключи не теряются) и патч Cline. Патч проверяется на
временной копии `state.vscdb`; живая база VS Code не трогается.

Тесты сборщика работают на временном проекте: проверяют, что шумные каталоги
(`node_modules`, `dist`, `.git`) не попадают в бриф, что списки entry/routes/db/
tests/configs наполняются, маркеры считаются только в коде, а CLI отдаёт 0/2 и
пишет `--out`.

Тесты бэклога проверяют канон: ID и даты, дубли, «надгробия», сверку дат с
журналом, close/open на временных файлах и сохранение CRLF.

Тесты эвалов проверяют сам измеритель: 10 задач с уникальными ID и критериями,
валидацию прогона, правило «последний прогон решает», подсчёт выдуманного и
среднего числа шагов, порог готовности и CLI (`list` / `record` / `score
--strict`). Битый файл результатов при ошибке не перезаписывается.

Тесты селектора покрывают разбор заголовков, bullet- и табличных пунктов,
маршрут (цитата → риск-домен → число файлов), карточку и CLI.

ВАША КОНФИГУРАЦИЯ (подтверждена владельцем)
--------------------------------------------------------------------------------
  GPU:  RTX 3060, 12 ГБ VRAM
  ОЗУ:  16 ГБ
  Вывод: профиль A — qwen2.5-coder:14b q4_K_M, ctx 12288.
  Папка называется "3060 16 gb" по объёму ОЗУ; видеопамяти — 12 ГБ.

Проверка одной командой (для отчёта и на будущее):

    nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv

Должно быть memory.total = 12 GiB. Если меньше (8 GiB) — берите профиль C.

Что даёт 16 ГБ ОЗУ, а что запрещает
  Разрешает: 14B q4 (~9 ГБ) целиком в VRAM + 1.5B (~1 ГБ) на автодополнение.
    Итого ~10 ГБ VRAM из 12, ОЗУ занята только Windows, VS Code и браузером.
  Запрещает: 14B q6/q8 и qwen3-coder:30b (19 ГБ) — это уже в ОЗУ, то есть
    "CPU/GPU split" и 3-5 ток/с вместо 30.
  Требует: не открывать одновременно Chrome на 30 вкладок, VS Code, Cline,
    MySQL, API и Vite preview. При 16 ГБ это реально ~7-8 ГБ, и первый
    запуск модели (она читается с диска в VRAM) лучше делать при закрытом
    браузере. Файл подкачки Windows не отключать.

Важно: модель обязана поместиться в VRAM ЦЕЛИКОМ. Как только Ollama начинает
выгружать слои в ОЗУ (в `ollama ps` видно "CPU/GPU split"), скорость падает с
30 ток/с до 3-5 ток/с. Проверка после первого запуска:

    ollama ps
    NAME                       ID     SIZE     PROCESSOR    UNTIL
    swiftmatch-coder-14b  ...    10 GB    100% GPU     30 minutes

Должно быть "100% GPU". Если нет — уменьшайте num_ctx или берите квант легче.
Для вашей карты ориентир: 14B q4 при ctx 12288 занимает ~10.1 ГБ, остаётся
~1.9 ГБ на десктоп Windows и CUDA. Если split всё равно появился — первым делом
поставьте num_ctx 8192 (KV-кэш падает с ~1.1 до ~0.75 ГБ).

ЧЕСТНЫЕ ОГРАНИЧЕНИЯ 14B НА 3060
--------------------------------------------------------------------------------
- 14B — это не DeepSeek и не Claude. Многофайловые задачи с длинной цепочкой
  рассуждений она проваливает чаще. Рабочая схема: локально — узкие правки и
  «прочитай/объясни», облако — большие задачи из бэклога.
- Контекст 12-16k токенов. Проект большой, поэтому правило простое: не давать
  агенту читать репозиторий целиком, только конкретные файлы.
- Качество 14B q4 заметно ниже 14B q6/q8. Если VRAM позволяет — профиль B.
- Скорость prefill на 3060 ~200-400 ток/с, это нормально: агент «думает» секунды,
  а не минуты, как на ноутбучном CPU.
- Электричество и нагрев: 3060 под нагрузкой 170 Вт, карта будет шуметь.


ЧЕГО НЕ ДЕЛАТЬ
--------------------------------------------------------------------------------
- Не запускать npm ci / npm install под работающим стеком: сначала удаляется
  node_modules, и на живом API это ломает дерево (EPERM). Останавливайте API.
- Не выполнять git reset --hard, git checkout -- <файл>, docker system prune:
  в проекте это стирает незакоммиченную работу и образы отката.
- Не держать в Cline авто-одобрение на запись файлов и команды, пока не
  убедитесь, что модель не «фантазирует» правки. Начните с read-only.
- Не включать одновременно облачную и локальную модель в одном запросе —
  контекст и деньги уходят впустую.

Этот файл — общая картина: кто что делает, что где запускается, где границы.
Подробности по шагам — в 07 (выбор задачи) и 08 (куда писать команды).


1. ОДНОЙ ФРАЗОЙ

  Скрипт выбирает задачу -> модель исполняет -> гейты проверяют ->
  человек коммитит.

  Модель НЕ решает, что делать, и НЕ решает, что «готово».
  Выбор задачи детерминированный (один и тот же бэклог -> одна и та же задача),
  проверка — машинная (exit 0 обязателен), решение о коммите — за человеком.


2. СХЕМА

  cmd в корне проекта
     |
     +- npm.cmd run stage:context      где мы: git, Stage, счётчики, очередь
     +- npm.cmd run stage:preflight    всё ли зелёное ДО работы
     +- npm.cmd run task:next -- --local
              |
              v
        карточка ~5 КБ (tmp/next-task.txt)
        ID - строка бэклога - file:line - ОДИН файл - гейты - промпт
              |
       +------+-------+
       v              v
    /next         /next-cloud
    3060           облако
    Ollama 14B     DeepSeek
    0 токенов      лимиты
       +------+-------+
              v
        правка одного файла
              v
    гейты: eslint - typecheck - vitest - check:docs / check:n-plus-one / ...
              v
    stage:checkpoint -> коммит поимённо -> push
    (шаг checkpoint выполняет человек: локальная модель не коммитит и не пушит)


3. КТО ЗА ЧТО ОТВЕЧАЕТ

  Компонент            Где                 Что делает                  Чего не делает
  -------------------  ------------------  --------------------------  ----------------------------
  next-task.mjs        CPU                 выбирает ОДНУ задачу из    не оценивает качество кода
                                           бэклога, режет до файла
  stage:preflight      CPU                 проверяет окно и гейты      не пишет код
  stage:checkpoint     CPU                 пишет Stage N.Y, коммитит    не чинит красные гейты
  Ollama (14B)         GPU 127.0.0.1:11434 исполняет узкую правку,      не тянет 4-5 файлов и
                                           объясняет файл              длинные цепочки
  Облако (DeepSeek)    сеть                многофайловые задачи, SQL,  не бесплатно, код уходит
                                           ревью, разбор гейтов        на чужой сервер
  OpenCode             терминал            харнесс: инструменты,       не выбирает задачи сам
                                           сессии, команды /next
  Cline                VS Code, панель     тот же агент на Ollama      нет API «принять задачу»
                                           или на облаке
  Continue             VS Code             серое автодополнение (1.5B) не правит файлы
  Человек              -                   читает дифф, говорит        -
                                           «делай», решает коммит


4. ЧТО ДЕЛАЕТСЯ НА 3060, А ЧТО В ОБЛАКЕ

  3060 (локально, бесплатно, код не уходит наружу):
    + одна правка в одном файле (карточка уже режет до одного файла);
    + «прочитай файл и объясни», поиск места по описанию;
    + переименования и мелкий рефакторинг внутри файла;
    + автодополнение в редакторе (модель 1.5B, чтобы не занимать VRAM);
    + тесты, линт, сборка — это вообще не модель, это CPU.

  Облако (DeepSeek через OpenCode):
    + всё, что шире одного файла: новые модули, миграции SQL, схема;
    + разбор красных гейтов и длинных логов;
    + ревью диффа перед коммитом;
    + тесты на 200+ строк;
    + планирование этапа.

  Правило эскалации (совпадает с routeFor в скрипте):
    - локальная ошиблась дважды на одной задаче -> /next-cloud;
    - в пункте нет цитаты «файл:строка» -> сразу /next-cloud (правило проекта);
    - деньги/Stripe, доступ и секреты, схема БД и миграции, деплой и
      инфраструктура -> сразу /next-cloud;
    - пункт на много файлов — это не повод для облака: карточка выдаёт один
      файл за подход, облако нужно, только если требуется обзор всех сразу;
    - после эскалации карточка та же, контекст не пересылается заново.

  Чего нет: автоматического «упало локально -> само ушло в облако».
  В OpenCode такого механизма нет. Маршрут задаётся до старта: строка
  model в файле команды или в конфиге, вручную — /models. Разбор четырёх
  уровней — 08, п.3.6.


5. ПОЧЕМУ ВЫБОР ЗАДАЧИ — СКРИПТ, А НЕ МОДЕЛЬ

  «Что доделать.txt» — около 18 тыс. токенов, контекст локальной модели 12288.
  Если отдать бэклог модели, она либо обрежет файл, либо начнёт выдумывать
  пункты. Поэтому:

    бэклог (18 тыс. токенов)  ->  скрипт  ->  карточка (5 КБ, ~500 токенов)

  пользователя», «Очередь этапов», и не берёт «Принятые решения» и «Не брать».
  Пункт без цитаты «файл:строка» не выдаётся (правило проекта).

8. ЧЕСТНЫЕ ГРАНИЦЫ

  1) 14B ошибается на многофайловых задачах чаще, чем хочется. Поэтому карточка
     режет работу до одного файла, а «остальные файлы — следующими подходами».
  2) «Зелёный eslint» не значит «корректный код». Замена any на unknown проходит
     линт и меняет смысл: 151 any (пункт QA-01) всё равно смотрят глазами.
  3) Полный автопилот не сделан осознанно: из трёх пунктов очереди два — блокеры
     владельца (ключи, домен, staging), третий — многочасовая работа с циклом
     «тест -> прогон -> фикс». Автоцикл упирается в лимит итераций на первом
     файле, а «зелёные гейты» не доказывают корректность.
  4) 12 ГБ VRAM хватает ровно на 14B + 1.5B. Третья модель одновременно даёт
     CPU/GPU split и падение с 30 до 3-5 ток/с.

ВАРИАНТ 1. OLLAMA CLOUD (самый простой: тот же localhost:11434)
--------------------------------------------------------------------------------
Вход выполняется один раз, модели НЕ скачиваются, идут через облако:

    ollama run gpt-oss:120b-cloud "напиши debounce на TypeScript"

Что доступно (облачные теги, проверено 30.10.2026 на живой машине):

    qwen3-coder:480b-cloud    ❌ отозван 15.07.2026 — НЕ использовать

ВАЖНО: список облачных тегов в Ollama меняется каждые несколько месяцев
(модели появляются, переименовываются и уходят). Эти строки — снимок
на дату комплекта, а не гарантия. Перед настройкой всегда проверяйте живой
список:  ollama.com/library  (облачные теги помечены -cloud), либо живой
список моделей после ollama signin. Если указанного тега нет, берите любую
доступную -cloud модель: меняется только строка ollama run и поле Model ID
в Cline, всё остальное в комплекте остаётся как есть.

В Cline ничего перенастраивать не нужно:
    API Provider: Ollama
    Base URL:     http://localhost:11434
    Model ID:     gpt-oss:120b-cloud

Плюсы: один провайдер на два режима, локальные модели остаются на месте.
Минусы: нужен интернет; на бесплатном тарифе — стартовые кредиты и ограничение
на число параллельных запросов, дальше платно по кредитам. Тарифы и лимиты
меняются: цифры смотрите на ollama.com/pricing, в комплекте они не фиксируются
(на 30.10.2026 не подтверждались).

Для вашей машины это плюс и по памяти: облачная модель не грузится в 12 ГБ VRAM
и не занимает 16 ГБ ОЗУ, поэтому рядом с облаком можно держать браузер и API.

ВАРИАНТ 3. OPENCODE + DEEPSEEK (второй агент, уже настроен в проекте)

В репозитории уже есть opencode.json:

То есть OpenCode читает правила проекта сам (персона + AGENTS.md) и НЕ нуждается

После первого запуска switch-ai.bat в этом же файле появятся model,
default_agent, providers.ollama.models и agents — скрипт мержит их, instructions
остаются на месте (бэкап opencode.json.bak-<дата>). Это штатное состояние;

    (б) переменная окружения или строка в .env проекта, заданная ДО запуска

    (в) перезапустить opencode после смены переменной — сервер подхватит её

ОЧИСТКА ЛОГА ПЕРЕД ОТПРАВКОЙ В ОБЛАКО (когда ошибка непонятная)
--------------------------------------------------------------------------------
Прежде чем вставлять лог в облачный чат, прогоните его через замену — email,
UUID, телефоны и ключи в логе не нужны ни одной модели:

  PowerShell, из папки с логом:

    (Get-Content app.log -Raw) `
      -replace '[\w.+-]+@[\w-]+\.[\w.]+','[EMAIL]' `
      -replace '[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}','[UUID]' `
      -replace '(?:\+7|8)[\s(-]*\d{3}[\s)-]*\d{3}[\s-]*\d{2}[\s-]*\d{2}','[PHONE]' `
      -replace '(sk|pk|whsec)_[A-Za-z0-9_]{8,}','[KEY]' `
      -replace '(password|token|secret)["'']?\s*[:=]\s*\S+','$1=[HIDDEN]' `
      | Set-Content app.clean.log

  Проверено на тестовом логе: email, UUID, оба формата телефона (+7 999 … и
  8 (999) …) и sk_live_… заменяются, а даты 2026-10-29 10:00:01 и ISO-метки
  остаются целыми (простая маска «много цифр подряд» съедала время в логе).

  Затем читать app.clean.log глазами (не вслепую) и только его отдавать
  в облако. В cmd то же самое делает любой редактор с regex-заменой
  (VS Code: Ctrl+H -> .* -> включить regex).

Важно: это грубая замена, гарантии она не даёт. Правило проще и надёжнее —
в облако идёт фрагмент кода и текст ошибки, а не лог целиком; ПДн, дампы
и .env не идут никогда. Если в логе остался один email — это уже утечка.

2. ЧТО ЧИТАЕТ СКРИПТ
================================================================================

Источник правды — только «Что доделать.txt» в корне проекта. Ничего не
выдумывается: нет пункта в файле — нет задачи.

Разбор:
  • разделы P0–P3, «Ждёт действий пользователя», «Очередь этапов» — берутся;
  • «Принятые решения», «Не брать», «Правила работы» — пропускаются целиком;
  • пункт без ID вида QA-01/P2-03 — не задача, игнорируется.

Статусы (главное отличие от первой версии):

  ready       — брать можно
  blocked     — заблокирована владельцем: ключи, домен, staging, юридический
                текст, «решение владельца», ENV-*/AND-*/CI-*/LEGAL-*
  closed      — уже сделана («закрыт Stage 162» и подобное)
  decision    — принятое решение, а не работа («риск принят», «осознанное
                ограничение»)
  watch       — отложена осознанно: в тексте `(watch: …)` или «не делать
                сейчас»; видна в --list, но в работу не выдаётся
  no-evidence — нет ни одного `файл:строка` / `файл` в тексте пункта

Правила выбора:
  • closed и decision не выдаются никогда, даже через --id;
  • blocked — только с явным --include-blocked;
  • watch — не выдаётся ни по умолчанию, ни с --local; текст пункта
    открывается через --id вместе с --include-blocked;
  • no-evidence — только с --allow-no-evidence;
  • один и тот же ID, встреченный дважды, схлопывается в одно вхождение,
    приоритет у того, где есть `file:line` (в бэклоге есть повторы).

5. КАК ЭТО ВСТРАИВАЕТСЯ В РАБОТУ
================================================================================

Полный цикл одного блока (5 шагов, ничего не выдумано — это правила проекта):

  1. npm.cmd run stage:context       — где мы: git, последний Stage, счётчики,
                                       открытые пункты очереди, гейты
  2. npm.cmd run stage:preflight     — всё ли зелёное ДО начала (tsc, eslint,
                                       счётчики, check:docs/mirrors/env-parity,
                                       окно 6 файлов / 300 строк)
  3. npm.cmd run task:next -- --local   — ОДНА задача и готовая карточка
  4. агент (Cline локально / OpenCode облако) исполняет карточку
     -> гейты из карточки, все должны быть exit 0
  5. npm.cmd run stage:checkpoint    — запись Stage N.Y в журнал, коммит
                                       поимённо, push; на красном окне не
                                       трогает ничего

Коммит и push на шаге 5 делает человек. Локальная модель (14B) не выполняет
git add / commit / push: она показывает дифф, гейты и список файлов, а решение
о коммите остаётся за владельцем (правило .clinerules 11.1). Скрипт
stage:checkpoint от этого не меняется — его просто запускает человек.

Пункты 1, 2, 5 — уже готовые скрипты проекта, я их не менял. Новое только 3.

Как отдать карточку агенту:
  • Cline: скопировать блок «ПРОМПТ ДЛЯ АГЕНТА» целиком в чат.
  • OpenCode: `opencode run "<вставить промпт>"` из корня проекта.
  • Файл: `npm.cmd run task:next -- --out tmp/next-task.txt`, затем открыть
    tmp/next-task.txt (каталог добавлен в .gitignore, в коммит не попадёт).

Чего в карточке нет намеренно:
  • нет «сделай хорошо» — только текст пункта и один файл;
  • нет права менять другие файлы без разрешения;
  • нет разрешения на any / as any / @ts-ignore;
  • нет автокоммита — коммит только через stage:checkpoint, после зелёных гейтов.

6. ЧЕСТНЫЕ ОГРАНИЧЕНИЯ
================================================================================

1. Скрипт выбирает, но не проверяет качество работы. «Зелёный eslint» на any не
   значит «типы правильные»: замена any на unknown проходит линт и меняет смысл.
   QA-01 всё равно смотрят глазами — по одному файлу.

2. Полный автопилот не сделан осознанно. Причина: из трёх пунктов очереди два —
   блокеры владельца, третий — многочасовая работа с циклом «тест → прогон →
   фикс». Автоцикл упрётся в лимит итераций на первом же файле, а «зелёные
   гейты» не доказывают корректность.

3. Пункты без цитаты кода (P2-01..P3-08, STORY-01, TEST-04) не выдаются: правило
   проекта — пункт без `file:line` не принимается. Это не баг скрипта.

4. Голое имя файла (`admin-queues.test.js` без каталога) достраивается по
   репозиторию, только если совпадение единственное. Если таких файлов два —
   путь остаётся как в бэклоге, и это видно в карточке.

5. Скрипт не меняет «Что доделать.txt». Закрытие пункта — ручная правка или
   stage:checkpoint, как и раньше.

6. Тесты скрипта лежат в scripts/ и не попадают в счётчики инвентаря
   (test-counter-audit считает только src/ и server/), поэтому гейт счётчиков
   они не сдвигают.

7. Маршрут «локально / облако» — это правило по ключевым словам, а не оценка
   сложности. Скрипт не читает код и не знает, сколько времени займёт правка.
   Ложное срабатывание в обе стороны возможно: «токен» в тексте задачи отправит
   её в облако, а тяжёлый рефакторинг без таких слов останется локальным.
   Поэтому строка «Маршрут» — совет, последнее слово за человеком.

8. Смена маршрута не переключает модель сама. Скрипт только печатает решение;
   запуск `opencode run` с моделью (локальной или облачной) делает человек или
   команда `/next` / `/next-cloud`. Автоматического «упало локально — ушло в
   облако» нет и не планируется.

2. ЧТО ДЕЛАЕТ 3060, А ЧТО ОБЛАКО

  На 3060 (локально, бесплатно, код не уходит наружу):
    + одна правка в одном файле (карточка next-task уже режет до одного файла);
    + «прочитай файл и объясни», поиск места по описанию;
    + мелкий рефакторинг внутри файла, переименования;
    + автодополнение в редакторе (1.5B);
    + запуск тестов/линта/сборки — это вообще не модель, это CPU.

  В облако (DeepSeek через OpenCode):
    + всё, что шире одного файла: новые модули, миграции SQL, схема;
    + разбор красных гейтов и длинных логов;
    + ревью диффа перед коммитом;
    + написание тестов на 200+ строк;
    + планирование этапа (stage:context -> план -> задачи).

  Почему именно так: 14B уверенно держит ~1 файл. Как только задача требует
  помнить 4-5 файлов и вызывать инструменты подряд, она начинает «терять»
  правки — и переделка стоит дороже, чем сэкономленные токены.

  Куда уйдёт конкретная задача, скрипт говорит сам — строкой «Маршрут» в
  карточке (и одной строкой в `--route`). Решение принимается по трём
  признакам: нет цитаты `file:line` -> облако; текст пункта или путь файла
  попал в риск-домен (деньги/Stripe, доступ и секреты, схема БД и миграции,
  деплой и инфраструктура) -> облако; иначе -> 3060 по одному файлу за
  подход. Это ключевые слова, а не оценка сложности: скрипт не читает код,
  поэтому последнее слово за человеком (07, п.6.7).

  ПРАВИЛО ЭСКАЛАЦИИ (простое и проверяемое):
    - локальная модель ошиблась дважды на одной задаче -> /cloud;
    - правка требует видеть больше одного файла СРАЗУ -> /cloud
      (если файлы идут по одному подходу — 3060 справится, карточка режет);
    - задача про деньги/безопасность/схему БД -> сразу /cloud;
    - после эскалации карточка та же, контекст не пересылаем заново.

  Решает это человек, а не модель: Cline и 14B не умеют оценивать свои
  пределы. Что скрипт может сказать заранее — строку «Маршрут» в карточке
  (число подходов или «нужен обзор всех файлов»).

  Чего НЕТ и не будет: автоматического «локальная упала -> само ушло в
  облако». OpenCode так не умеет (в документации такого механизма нет).
  Но выбор модели делается детерминированным заранее: файл команды в
  .opencode/commands/ несёт строку model, поэтому /next всегда идёт на
  3060, а /next-cloud — в облако. Строка за строкой — п.3.6.


3. НАСТРОЙКА OPENCODE НА ДОМАШНЕМ ПК

  3.1 OpenCode берёт модели Ollama сам: если Ollama слушает
      http://127.0.0.1:11434 (порт по умолчанию), то в /models появятся
      ollama/swiftmatch-coder-14b и ollama/swiftmatch-coder-tiny.
      Отдельный провайдер прописывать не нужно.

  3.2 Два агента в opencode.json проекта (рядом с AGENTS.md):

      МЕРЖИТЬ, А НЕ ЗАМЕНЯТЬ. В файле уже есть ключ instructions — он подключает
      правила проекта (persona + AGENTS.md). Если заменить файл целиком примером
      ниже и потерять instructions, агент останется без правил. Полный файл
      «как должно получиться» — 10-Приложения.txt, раздел 3.

      {
        "$schema": "https://opencode.ai/config.json",
        "instructions": [".opencode/persona.md", "AGENTS.md"],
        "model": "ollama/swiftmatch-coder-14b:latest",
        "default_agent": "local",
        "providers": {
          "ollama": {
            "models": {
              "swiftmatch-coder-14b:latest": {
                "name": "swiftmatch-coder 14B q4 · ctx 12k",
                "limit": { "context": 12288, "output": 4096 },
                "capabilities": {
                  "tools": true,
                  "input": ["text"],
                  "output": ["text"]
                }
              }
            }
          }
        },
        "agents": {
          "local": {
            "description": "Основная работа на 3060: один файл, узкая правка",
            "mode": "primary",
            "steps": 10,
            "permissions": [
              { "action": "webfetch", "resource": "*", "effect": "deny" },
              { "action": "websearch", "resource": "*", "effect": "deny" }
            ]
          },
          "cloud": {
            "description": "Эскалация: многофайловые задачи, ревью, миграции",
            "mode": "primary",
            "model": "opencode/deepseek-v4.1-flash-free"
          }
        }
      }

      Пояснения:
        model            = что берётся по умолчанию (3060);
        default_agent    = какой агент стартует (local);
        steps: 10        = предохранитель от зацикливания 14B (поле steps;
                           устаревшее maxSteps не использовать);
        permissions      = упорядоченный массив правил action/resource/effect
                           (форма V2; старый объект permission ещё читается,
                           но помечен устаревшим);
        providers.ollama.models = описания сборок: контекст и поддержка
                           инструментов; облачные -cloud теги сюда же;
        cloud            = тот же OpenCode, но на облачной модели.

      Ключи именно такие (сверено с OpenCode V2, 30.10.2026): providers, agents,
      permissions — множественное число. Старые provider / agent / permission
      V2 ещё принимает, но в новых файлах их не используем и не смешиваем
      форматы внутри одного агента. Ошибка в имени ключа не роняет OpenCode —
      он просто молча игнорирует блок, и агент остаётся с настройками по
      умолчанию.

      Имя облачной модели подставьте своё — то, что реально подключено у вас
      (посмотрите /models). Если модель не найдена, OpenCode берёт ближайшую
      доступную, поэтому лучше проверить глазами.

  3.3 Две команды для переключения (файлы в .opencode/commands/):

      .opencode/commands/local.md
        ---
        description: Выполнить задачу на локальной модели (3060)
        agent: local
        model: ollama/swiftmatch-coder-14b:latest
        ---
        $ARGUMENTS

      .opencode/commands/cloud.md
        ---
        description: Эскалация в облако
        agent: cloud
        model: opencode/deepseek-v4.1-flash-free
        ---
        $ARGUMENTS

      Работает так:
        /local почисти any в src/pages/chats.tsx      (3060, бесплатно)
        /cloud сверь схему миграций с mysql_schema   (облако)

      Строка model — главная: без неё команда лишь переключает агента, а
      модель остаётся той, что выбрана в сессии. С ней маршрут жёсткий и
      повторяемый (п.3.6).

  3.4 Если облако нужно не агентом, а одной задачей из терминала:
        opencode run --model opencode/deepseek-v4.1-flash-free "<карточка>"
      Флаг --model для run документирован; наличие --agent проверяйте через
      opencode run --help (выдумывать не буду).

  3.5 ВАЖНО: не включайте этот конфиг на машине, где моделей Ollama ещё нет
      (например на ноутбуке). Порядок: сначала 02-Установить-локально.bat,
      проверка ollama list (должны быть swiftmatch-coder-14b и
      swiftmatch-coder-tiny), и только потом правка opencode.json.


  3.6 КАК РЕАЛЬНО ВЫБИРАЕТСЯ МОДЕЛЬ (проверено по документации OpenCode V2)

      Скрипт next-task.mjs модель НЕ выбирает: у него нет ни ключей, ни
      доступа к API, ни памяти «ошиблась дважды». Он решает ЧТО делать и
      режет задачу до карточки (~5 КБ). ГДЕ это делать решают четыре уровня,
      от самого сильного к самому слабому:

        1. model в шапке команды (frontmatter) — перекрывает всё остальное
           Модель задаёт файл команды, а не модель и не скрипт:

             ---
             description: Следующая задача для 3060
             agent: local
             model: ollama/<точный ID из /models>
             ---

           Так /next жёстко уходит на 3060, а /next-cloud — в облако.
           Это и есть детерминированный автовыбор: решение принимает
           конфигурация, один и тот же бэклог даёт один и тот же маршрут.

           В нынешних next.md и next-cloud.md строки model нет — они
           выбирают задачу, а модель берут из сессии. Чтобы маршрут стал
           жёстким, добавьте строку model (ID — из /models) в шапку файла.

        2. model у агента (opencode.json, блок agents:
           Работает, когда у команды своей строки model нет.

        3. /models — модель текущей сессии, вручную
           Меняет только сессию, файл конфига не переписывает.

        4. opencode run --model provider/model "<промпт>" — на один запуск
           Ничего не меняет в конфиге.

      Развилки «Ollama локально ИЛИ OpenCode» не существует. Это два разных
      вопроса:
        • ЧЕМ исполнять — Cline в VS Code или OpenCode в терминале. Оба умеют
          править файлы, оба видят один и тот же проект;
        • НА ЧЁМ считать — локальная модель Ollama на 3060 или облачная.
          OpenCode прекрасно работает на локальной Ollama (он сам её находит,
          см. ниже), а Cline можно направить в Ollama Cloud (gpt-oss:120b-cloud
          после ollama signin) или в DeepSeek/OpenRouter по ключу.
      Скрипт next-task.mjs отвечает только на второй вопрос (local/cloud) и
      печатает это в строке «Маршрут»; чем исполнять — решает человек.

      Про агентов отдельно: переключение primary-агента — клавиша Tab (цикл),
      список агентов — opencode agent list. Команд «/agents» и
      «/agents select <имя>» в OpenCode НЕТ (в TUI-командах их не существует).
      И выбранный агент сам модель сессии не меняет — модель берётся
      уровнями 1, 2 или 3.

      Ollama подключать не надо: OpenCode сам находит её на 127.0.0.1:11434
      и показывает модели как ollama/<имя>. Отдельный блок providers не
      нужен. Точный ID брать в /models, а не угадывать: тег Ollama может
      быть частью имени (qwen2.5-coder:14b, у своей сборки — :latest).
      Если ID не совпал, команда отвечает «Model unavailable» и не делает
      ничего, поэтому строку model вписывать только после проверки.

      Облачные модели Ollama (теги -cloud после ollama signin) — это тот же
      провайдер ollama, просто модель считается не на 3060. Для OpenCode это
      такая же запись ollama/<имя>-cloud: отдельного «облачного провайдера»
      нет, и перехода на неё «когда не хватило VRAM» тоже нет.

      Запуск OpenCode сразу на нужной модели Ollama (0.40+):
        ollama launch opencode --model swiftmatch-coder-14b


4. ОДНА ФРАЗА: «ДОДЕЛАЙ ИЗ ЧТО ДОДЕЛАТЬ» — КУДА ВВОДИТЬ

  4.1 OpenCode (терминал):
        /next              узкая задача для 3060 (только file:line)
        /next-cloud        по приоритетам бэклога (для облака)
        /next QA-01        конкретный пункт
      Файлы команд: .opencode/commands/next.md и next-cloud.md.
      В комплект и в проект они НЕ входят: каталога .opencode нет.
      Создайте вручную по п.3.3; без файлов /next отвечает «команда не найдена».
      Модель эти команды не выбирают (строки model в них нет): её берёт
      сессия. Жёсткий маршрут «/next = 3060, /next-cloud = облако» —
      одна строка model в шапке файла, см. п.3.6.

  4.2 Cline (панель в VS Code):
        просто напишите:  Доделай из Что доделать
      Правило в .clinerules (п.10) обязывает агента сначала выполнить
      node scripts/next-task.mjs --local --out tmp/next-task.txt,
      прочитать карточку и работать только по ней.

  4.3 cmd (совсем без модели, только карточка):
        npm.cmd run task:next -- --local
        start tmp\next-task.txt

  Почему нельзя просто «прочитай бэклог и сделай»:
      «Что доделать.txt» ~18 тыс. токенов, контекст 12288. Модель либо
      обрежет файл, либо начнёт выдумывать пункты. Скрипт режет бэклог до
      карточки ~5 КБ, и модель видит ровно одну задачу и один файл.

  Что происходит по шагам:
      1) скрипт выбирает задачу детерминированно (не модель);
      2) печатает карточку: ID, строка бэклога, цитата file:line, один файл,
         гейты, готовый промпт;
      3) агент читает ТОЛЬКО карточку;
      4) показывает план 3-5 пунктов, ждёт «делай»;
      5) правит один файл, гоняет гейты, отчитывается.

  Важно про 3060: если создадите команды /next и /next-cloud по п.3.3, без
  полей agent/model они работают на той модели, что выбрана в сессии.
  После установки моделей Ollama добавьте в frontmatter две строки:
      /next:        agent: local     model: ollama/swiftmatch-coder-14b:latest
      /next-cloud:  agent: cloud     model: opencode/deepseek-v4.1-flash-free


5. ПОРЯДОК ПЕРВОГО ДНЯ НА ДОМАШНЕМ ПК

   1) Драйвер NVIDIA: nvidia-smi показывает карту, memory.total = 12 GiB.
   2) Ollama установлена: ollama --version.
   3) 02-Установить-локально.bat -> профиль [1] (14B q4), затем ещё раз -> [4]
      (1.5B для автодополнения).
   4) Закрыть Ollama в трее и запустить заново (переменные окружения).
   5) 03-Замер-скорости.bat -> "eval rate" 25-35 ток/с, ollama ps -> 100% GPU.
      Если 3-5 ток/с — модель не влезла в VRAM, ставьте num_ctx 8192.
   6) ollama list -> есть swiftmatch-coder-14b и swiftmatch-coder-tiny.
   7) VS Code + расширения (Cline, Continue, ESLint, Tailwind).
   8) Открыть swiftmatch-3060.code-workspace.
   9) Установить правила и память в проект:
      node "D:\ИИ агент\3060 16 gb\scripts\init-project.mjs" --root . --dry-run
      затем без --dry-run. Скрипт создаст .clinerules, workflows и cline_docs.
  10) Вместо ручной вставки блока 3.2 и файлов 3.3: закрыть VS Code, из корня
      проекта выполнить switch-ai.bat local (или local-q5) — скрипт сам
      смержит opencode.json и настроит Cline (см. 12-Переключение-моделей.txt).
      Ручной путь оставьте, если нужно понять, что именно меняется.
  11) Проверка связки: открыть cmd в проекте, выполнить
          npm.cmd run stage:context
          npm.cmd run task:next -- --local
      Взять карточку, отдать в Cline (локально) или в /local (OpenCode).
  12) Continue: положить 06-...yaml в %USERPROFILE%\.continue\config.yaml,
      перезапустить VS Code, проверить серые подсказки.


6. ЧЕГО НЕ ДЕЛАТЬ

   - Не запускать npm install / npm ci под живым API (EPERM, полусломанное
     дерево). Сначала остановить стек.
   - Не давать локальной модели задачу «почини весь проект» — она вернёт
     10 файлов с выдуманными правками.
   - Не включать авто-одобрение записи и терминала в Cline на 14B.
   - Не держать в VRAM одновременно 14B и 7B «на всякий случай»: 12 ГБ
     хватает на 14B + 1.5B, третий моделью начнётся CPU/GPU split.
   - Не пересылать в облако .env, ключи, дампы БД. Карточки из next-task
     содержат только пути и текст бэклога — их можно.
