1. MODELEFILE: ОТКУДА БЕРЁТСЯ 10.1 ГБ ИЗ 12

  Файл: models\Modelfile-14b-q4 (он же в комплекте, папка models\)

      # Профиль A: RTX 3060 12 ГБ VRAM (стандартная карта)
      # Модель целиком в VRAM: 9.0 ГБ веса + ~1.1 ГБ KV-кэш (q8) = ~10.1 ГБ из 12.
      # Ожидаемая скорость: 25-35 ток/с генерация, 200-400 ток/с prefill.

      FROM qwen2.5-coder:14b

      PARAMETER num_ctx 12288
      PARAMETER num_gpu 99
      PARAMETER temperature 0.2
      PARAMETER top_p 0.9

  Три строки, которые нельзя терять:
    FROM               базовый тег из ollama pull; если тега нет, pull упадёт
    num_ctx 12288      без этой строки Ollama возьмёт дефолт 4096 и начнёт
                       резать файлы — самая частая «загадка» локальных моделей
    num_gpu 99         просит уложить все слои в GPU; при нехватке VRAM
                       Ollama сама сделает split и покажет его в ollama ps

  Остальные четыре профиля отличаются только этими значениями:
    Modelfile-14b-q6    FROM qwen2.5-coder:14b-instruct-q6_K, num_ctx 16384
                        (профиль B: только для 16 ГБ VRAM)
    Modelfile-7b-q8     FROM qwen2.5-coder:7b-instruct-q8_0,  num_ctx 16384
    Modelfile-7b-q5     FROM qwen2.5-coder:7b-instruct-q5_K_M, num_ctx 16384
                        (профиль E: 5.4 ГБ веса, ~6.5 ГБ с KV — запас VRAM)
    Modelfile-tiny      FROM qwen2.5-coder:1.5b,             num_ctx 4096

  Обратите внимание: у 14B q4 контекст 12288 намеренно меньше, чем у q6 и 7B.
  На 3060 12 ГБ каждый лишний килобайт контекста — это KV-кэш в той же VRAM,
  а для карточки в 5 КБ и правки одного файла 12288 хватает с запасом.

  Проверка после установки (обязательна):
      ollama show swiftmatch-coder-14b --modelfile | findstr num_ctx
      ожидается: PARAMETER num_ctx 12288
      ollama ps      ->  колонка PROCESSOR = 100% GPU

  ## 10. Триггер «Доделай из Что доделать»

  Если человек пишет «Доделай из Что доделать», «следующая задача»,
  «что дальше»:

     в контекст 12288.
  2. Выполни в терминале: node scripts/next-task.mjs --local --out tmp/next-task.txt
     (если назван ID — --id <ID>).
  3. Прочитай только tmp/next-task.txt.
  4. Работай строго по разделу «ПРОМПТ ДЛЯ АГЕНТА»; файл — из раздела
     «СРЕЗ ДЛЯ ОДНОГО ПОДХОДА», другие файлы не трогай.
  5. Exit 1 от скрипта значит «брать нечего»: покажи
     node scripts/next-task.mjs --list.
  6. Текст задачи берётся из карточки, из памяти модели — нельзя.

  ## 11. Локально или в облако

  Локальная модель (14B на 3060): одна правка в одном файле, объяснение файла,

  ## 11.1 Кто делает коммит

  Статусы пункта:
      ready       можно брать (для --local нужен ещё evidence = file:line
                  и маршрут local)
      blocked     ждёт внешнего действия (ключи, домен, staging)
      closed      выполнено — не выдаётся даже через --id

      no-evidence открыто, но без цитаты file:line — по умолчанию не выдаётся

  Что гарантирует скрипт:
    - детерминированность: тот же бэклог -> та же задача, решение не за моделью;
    - дедупликация по ID: один пункт не выбирается дважды под разными именами;
    - разрешение «голого» имени файла (chats.tsx -> src/pages/chats.tsx) только
      при единственном совпадении в репозитории, папка test/ исключена;
    - карточка содержит ID, строку бэклога, цитату file:line, ОДИН файл,
      гейты и готовый промпт для агента;
    - строка «Маршрут» в карточке (функция routeFor, экспортируется):
          нет цитаты file:line           -> облако: такой пункт не берут
          риск-домен (см. ниже)          -> облако (/next-cloud): <домен>
          один файл + file:line          -> 3060: один файл, один подход
          несколько файлов (N)           -> 3060 по одному файлу, подходов: N
                                            (+ подсказка про /next-cloud)
      Порядок именно такой: сначала правило проекта (цитата), потом риск,
      потом число файлов. Риск-домены ищутся по тексту пункта и по путям

                  IDOR, rate-limit, пароль, sanitiz, XSS, SQL-инъекция

                  schema, схема, индекс

      Это ключевые слова, а не оценка сложности и не проверка кода. Скрипт

      решение, а запуск модели остаётся за человеком;

    - `--route` печатает ровно одно решение в формате `local<TAB>текст` или

      в поле `route` ({ target, reason, text }), где reason — одно из
      no-citation / money / access / schema / infra / single-file / stepwise;
    - заблокированный бэклог (файл открыт в Excel/Word/редакторе, held другой

8. ВОПРОС «ДЕЛАТЬ В OLLAMA ЛОКАЛЬНО ИЛИ ЧЕРЕЗ OPENCODE»: РАЗВИЛКИ НЕТ,
   ОПРЕДЕЛЕНИЕ МАРШРУТА УСИЛЕНО

  8.1 ГЛАВНОЕ. «Ollama локально» и «OpenCode» — не альтернатива друг другу.
      Это два независимых вопроса:
        • НА ЧЁМ считать: локальная модель на 3060 или облачная. Только это
          и решает скрипт (local / cloud);
        • ЧЕМ исполнять: Cline в VS Code, Continue (автодополнение) или
          OpenCode в терминале. OpenCode работает и на локальной Ollama —
          он сам находит её на 127.0.0.1:11434 и показывает модели как
          ollama/<имя> (08, п.3.6). Cline точно так же можно направить
          в облако ключом DeepSeek.
      Отсюда практический вывод: держать две обвязки (Cline для локали,
      OpenCode для облака) не обязательно. Можно работать в одной, меняя
      только модель сессии или шапку команды.

  8.2 ЧТО УСИЛЕНО В КОДЕ. Раньше routeFor смотрел ровно один признак —
      число файлов; из-за этого «добавить миграцию в одном файле» уходило
      на 3060. Теперь решение принимается по трём признакам в порядке
      приоритета:
        1) нет цитаты file:line                    -> cloud (правило проекта);
        2) риск-домен в тексте пункта или пути файла -> cloud;
        3) иначе                                   -> local, по одному файлу.
      Риск-домены: money (платежи, Stripe, подписка, возврат, выплата,
      комиссия), access (JWT, auth, CSRF, adminAuth, секрет, токен,
      уязвимость, IDOR, rate-limit, пароль, XSS, SQL-инъекция), schema
      (миграция, mysql_schema, ALTER/CREATE TABLE, ENUM, CHECK, индекс),
      infra (docker, compose, deploy.yml, nginx, деплой, kubernetes).
      Причина в карточке печатается явно: «облако (/next-cloud): <домен>».
      Это ключевые слова, а не оценка сложности — так и написано в карточке:
      «скрипт смотрит ключевые слова, сложность он не оценивает».

  8.3 НОВЫЕ ФЛАГИ. `--route` печатает только решение одной строкой
      (`local<TAB>текст` / `cloud<TAB>текст`) и не печатает карточку —
      удобно для скриптов и для быстрой проверки «куда уйдёт задача».
      `--local` теперь фильтрует через routeFor, то есть не выдаёт пункты
      риск-домена (раньше проверялась только цитата). В `--json` добавлено
      поле route = { target, reason, text }, reason — одно из no-citation /
      money / access / schema / infra / single-file / stepwise.

  8.4 ЧЕСТНО О ГРАНИЦАХ. Ложные срабатывания возможны в обе стороны:
      слово «токен» в тексте отправит задачу в облако, а тяжёлый
      рефакторинг без таких слов останется локальным. Скрипт не читает код.
      Автоматического «упало локально — ушло в облако» по-прежнему нет:
      маршрут печатается, запуск модели делает человек (07, п.6.7–6.8).

  8.5 ПРОВЕРЕНО. scripts/next-task.mjs — 597 строк, scripts/next-task.test.mjs
      — 46 тестов (было 38: добавлены платежи, доступ, схема, инфра,
      ключевое слово в пути, честность формулировки, фильтр --local).
      vitest: 46 passed; eslint по обоим файлам: exit 0. Живой прогон:

6.1 OPENCODE — opencode.json

  Скрипт правит только то, что относится к маршруту:

    model          — модель по умолчанию для новых сессий;
    default_agent  — local (без сети, 10 шагов) или cloud;
    providers.ollama.models — описания сборок комплекта и облачного тега
                     (контекст и поддержка инструментов; облачные теги
                     не всегда попадают в автодискавери Ollama);
    agents         — шаблоны агентов local/cloud, если их ещё нет.

  Остальное сохраняется: instructions (persona + AGENTS.md), чужие провайдеры,
  ваши агенты, тема и любые другие ключи. Это мерж, а не замена файла.
  Перед записью создаётся opencode.json.bak-<дата>.

  Ключи — в актуальной форме OpenCode V2: providers, agents, permissions.
  Старые provider / agent / permission OpenCode V2 ещё читает, но они помечены
  устаревшими; новые примеры в 08 и 10 — тоже V2.

  Важно: config читается при старте OpenCode. Уже открытая сессия хранит
  выбранную модель отдельно — переключите её через /models или начните новую.
  Если модель не сменилась даже в новой сессии, перезапустите opencode.

6.2 CLINE — state.vscdb

  Cline хранит провайдера и модель не в settings.json, а в globalState VS Code:

    %APPDATA%\Code\User\globalStorage\state.vscdb
    ключ saoudrizwan.claude-dev

  Скрипт обновляет:

    apiProvider, apiModelId,
    planModeApiProvider, actModeApiProvider,
    planModeApiModelId, actModeApiModelId,
    ollamaModelId, ollamaBaseUrl, ollamaApiOptionsCtxNum,
    planModeOllamaModelId, actModeOllamaModelId

  Авто-одобрение, чекпоинты и остальные настройки НЕ трогаются.

  Требования:

    1) VS Code закрыт. Иначе скрипт откажется писать: VS Code перезапишет
       состояние при выходе. Обойти можно --force, но это риск потери настроек;
    2) после записи открыть VS Code заново: Cline читает состояние при старте;
    3) проверить: Cline -> шестерёнка -> API Configuration;
    4) перед записью создаётся state.vscdb.bak-<дата> рядом с базой.

  Поддерживаются VS Code stable и Insiders; если Cline ещё ни разу не
  запускался, скрипт честно скажет, что state.vscdb не найден.

2. ПОЧЕМУ «ПО ШАБЛОНУ»
--------------------------------------------------------------------------------

  Симптом                          Причина
  -------------------------------  --------------------------------------------

3. СБОРЩИК ФАКТОВ: scripts/project-brief.mjs
--------------------------------------------------------------------------------

Детерминированный, без зависимостей, только встроенные модули Node. Ничего не
меняет и не ходит в сеть. Обходит дерево, пропуская .git, node_modules, dist,
build, out, coverage, .next, .cache, tmp, vendor, .venv, __pycache__ и т.п.

Что печатает:

  root, git (ветка, последний коммит, число изменённых файлов)
  package: имя, версия, scripts, зависимости, devDependencies
  files: сколько файлов (без шума), крупнейшие каталоги
  entry:    точки входа из package.json (main/module/bin) и по имени
  routes:   routes/, controllers/, pages/api/, api/
  db:       migrations/, *.sql, schema.prisma, models/
  tests:    __tests__/, test/, *.test.*, *.spec.*
  configs:  tsconfig, eslint, vite, webpack, jest, vitest, Dockerfile, .env.example,
            .clinerules, AGENTS.md, opencode.json
  largest:  самые крупные файлы с размером
  markers:  TODO, FIXME, any, @ts-ignore, @ts-expect-error, eslint-disable

Ограничения (чтобы не зависнуть на гигантском репозитории):

  - файл больше 512 КБ в счётчики маркеров не попадает;
  - маркеры смотрятся максимум в 4000 файлах;
  - «any» считается только в JS/TS, иначе слово ловится в тексте Python/Go.

Команды:

    node scripts/project-brief.mjs
    node scripts/project-brief.mjs --root "D:\путь\к\проекту"
    node scripts/project-brief.mjs --root . --out tmp\brief.txt
    node scripts/project-brief.mjs --json
    node scripts/project-brief.mjs --limit 10
    node scripts/project-brief.mjs --help

  --root   корень проекта (по умолчанию текущий каталог)
  --out    записать в файл (UTF-8) вместо печати
  --json   машинный вывод для скриптов
  --limit  сколько элементов в каждом списке (по умолчанию 20)

Коды выхода: 0 — готово, 2 — ошибка аргументов или нет такого каталога.
Скрипт лежит в комплекте и работает с любым каталогом через --root; копировать
его в проект не обязательно.

Пример брифа (сокращённо):

    routes: src/pages/api/health.ts, src/routes/orders.ts
    db: db/migrations/0012_orders.sql
    tests: tests/orders.test.ts
    configs: tsconfig.json, vite.config.ts, .clinerules
    largest:
      src/lib/pricing.ts — 84 КБ

    каждое утверждение подкрепи file:line. Бриф сам по себе — не факт.

    - ссылаться на файл, который не открывался;
    - писать «вероятно», «обычно», «как правило» без пометки «догадка»;
    - предлагать рефакторинг всего проекта;
    - делать вывод по одному имени файла.

ПРОХОД 2 — СИНТЕЗ (облако, если нужен):

    - на вход идут не файлы целиком, а карточка прохода 1 (факты + цитаты);
    - облако отвечает на вопрос «что делать», опираясь на эти факты;
    - если фактов не хватает, оно возвращает список файлов, а не выдумывает.

  Карточка — это интерфейс между проходами. Без неё облако снова начнёт
  угадывать по названиям. Шаблон: templates/analysis-card.md.

  Проверка результата человеком (30 секунд):

    - открыть 2-3 cited file:line и убедиться, что строка существует;
    - найти в ответе хотя бы одно утверждение без цитаты — это и есть «шаблон»;
    - если такое есть, ответ возвращается на доработку, а не в работу.

8. ПРО ДООБУЧЕНИЕ (LoRA) — ПОЗЖЕ
--------------------------------------------------------------------------------

  Сейчас «обучение» = контекст + протокол + проверка. Этого достаточно: модель
  уже умеет читать файлы, ей не хватает discipline, а не весов.

  LoRA имеет смысл только когда упрётесь в формат: модель стабильно игнорирует
  карточку, путает разделы, не ставит цитаты. Тогда:

    - собрать 200-500 пар «бриф + файлы -> карточка с цитатами»;
    - учить на своём формате ответа, а не на «знании проекта»;
    - проверять на отложенных 50 примерах, а не на обучающих;
    - держать базовую модель рядом: LoRA не должна ухудшать чтение кода.

  До этого этапа LoRA — трата времени: формат ответа дешевле задать правилами
  и шаблоном, чем обучением. Подробнее — «Что доделать», раздел 3.

  решение, а не инструкция.
- `Обучение ИИ.md` — исследовательский материал: идеи и альтернативные
  инструменты, не инструкции комплекта.
- `Анализ ИИ агентов.md` — дамп диалога про харнессы (agentkai, Iridium,
  AgenticSeek, MCP) и сверка с фактами комплекта; часть чисел без источника.
- `docs/archive/` — исходные `.txt` этих трёх разборов (срез 31.10.2026,
  перенесены 31.10.2026). Только история: факты о коде агент берёт из кода, а
  не отсюда. Нумерация строк в `.txt` сдвинута шапкой архива.
- `backups/`, `coverage/`, `logs/`, `test-analysis/`, `vitest-*.json` — данные
  прошлых прогонов. Для агента это не источник фактов о коде.

## Гигиена

- Одно правило — один файл. Не копировать блоки между `.md`, а ссылаться.
- Новые правила не добавлять в корневые `.txt`: там только состояние.
- Если файл не упомянут в `README.md`, `00-ЧИТАЙ-ПЕРВЫМ.txt` или здесь, он
  считается архивом.
- Устаревший документ не удалять молча: перенести в `docs/archive/` и указать
  дату среза.

# Настройка Cline под локальную 14B

> Это настройки инструмента, а не код проекта. Без них правила лежат в
> `.clinerules`, но модель не получает их в нужном объёме: полный системный
> промпт Cline съедает контекст 12288 быстрее, чем файл задачи.

## 1. Compact Prompt

- Откройте настройки Cline (⚙) → **Features** → включите **Use Compact
  Prompt**.
- Если пункта нет в вашей версии — обновите расширение; в старых сборках
  компактного промпта нет.
- Проверка: в новом чате попросите «перечисли свои правила одной строкой».
  Если ответ содержит блоки `RESTATE → MAP → PLAN → ACT → VERIFY → REPORT`,
  правила прочитаны. Если нет — `.clinerules` лежит не в корне проекта.

## 2. Параметры генерации

| Параметр | Значение | Зачем |
|---|---|---|
| Context window | `12288` | 14B Q4 на 12 ГБ; выше — риск CPU/GPU split |
| Max output tokens | `2048–4096` | длинный ответ обрезается, а не съедает VRAM |
| Temperature | `0.1–0.3` | код и цитаты, а не «творческий» пересказ |
| Top P | `0.9` | оставить, если поле есть |
| Stop sequences | `<|im_end|>`, `<|endoftext|>` | если поле есть; Ollama обычно добавляет сам |

Правило: не поднимать context выше 16384 без `ollama ps` — если модель ушла
в RAM, скорость падает с 25–35 до 3–5 ток/с.

## 3. Confidence Check

Добавьте в проектный `.clinerules` (или используйте `40-agent-cycle.md`):

```text
Перед первым инструментом оцени уверенность в том, что понял задачу и
нашёл правильный файл, по шкале 0–10.
- 7–10: действуй по циклу.
- 4–6: задай один уточняющий вопрос.
- 0–3: остановись, перечисли, чего не хватает, и предложи облако.
```

Это не заменяет проверку: модель может быть уверена и ошибаться. Confidence
Check нужен, чтобы она чаще останавливалась до правки, а не после.

## 4. Маршрут моделей

| Задача | Профиль |
|---|---|
| одна правка в одном файле, объяснение файла | локальная 14B (`local`) |
| рутина, автодополнение, быстрый поиск | 7B (`local-q5` / `local7`) |
| больше одного файла, SQL и схема, миграции, ревью диффа | облако (`cloud`) |

Переключение — `switch-ai.bat local` / `switch-ai.bat cloud` из корня проекта.
Cline при закрытом VS Code, OpenCode — новая сессия или `/models`.

## 5. Memory Bank

Шаблоны `cline_docs/` создаёт установщик:

```bat
node "E:\3060OllamaClineOpenCode-main\scripts\init-project.mjs" --root . --dry-run
node "E:\3060OllamaClineOpenCode-main\scripts\init-project.mjs" --root .
```

Порядок работы:

1. **initialize** — прочитать все `cline_docs/*.md`, заполнить
   `projectBrief.md`, `techContext.md`, `systemPatterns.md`; в
   `activeContext.md` записать текущую задачу и план.
2. **update** — в конце каждой задачи обновить `activeContext.md` (что
   сделано, следующий шаг) и `progress.md` (что проверено, что нет).
3. **archive** — устаревшие решения не удалять молча: перенести в
   `cline_docs/archive/` с датой.

Не хранить в `cline_docs/` секреты, токены и персональные данные.

## 6. Проверка после настройки

- [ ] Compact Prompt включён.
- [ ] Context 12288, max output 2048–4096, temperature 0.1–0.3.
- [ ] `.clinerules/40-agent-cycle.md` и `50-few-shot.md` на месте.
- [ ] `cline_docs/activeContext.md` заполнен.
- [ ] Cline отвечает на «где монтируются роуты?» с `file:line`, а не общими
      словами.
- [ ] `switch-ai.bat status` показывает локальную модель.
- [ ] `ollama ps` — `100% GPU`.

## 7. Чего не делать

- Не включать одновременно полный и компактный промпт «для надёжности».
- Не ставить temperature выше 0.4 для правок кода.
- Не давать локальной модели `git push`, миграции и живую БД.
- Не считать «зелёный линт» доказательством корректности: нужен тест и diff.

# Механика «Что сделано ↔ Что доделать»

> Взято из проекта SwiftMatch (`docs/AGENTS-workflow.md`) и адаптировано под
> комплект. Это единственный канон механики журналов: остальные файлы
> ссылаются сюда, а не пересказывают правила.

## 1. Две роли, один канон

| Файл | Что содержит | Чего в нём нет |
|---|---|---|
| `Что доделать.txt` | только **открытые** пункты с ID, фактом и датой проверки | истории, разбора закрытого, правил |
| `Что сделано.txt` | хроника: что и где сделано, `file:line`, тесты, гейты | открытых задач и очереди |

Журнал закрытий живёт только в `Что сделано.txt`. Третьей копии нет:
`Что доделать коротко.txt` и подобные свёртки запрещены — они расходятся с
каноном и вводят агента в заблуждение.

## 2. Форматы

Открытый пункт:

```text
### BLK-01 — Заголовок
Факт: что именно проверить, с `file:line` из кода.
Статус: ⏳ (проверено 30.10.2026)
```

Закрытый пункт:

```text
## ✅ BLK-01 — Заголовок (см. «Что сделано.txt»: раздел «BLK-01») — ЗАКРЫТО 30.10.2026
```

Правила:

- ID — `PREFIX-NN`, уникален в открытых и закрытых.
- Открытый пункт без `Статус: ⏳ (проверено ДД.ММ.ГГГГ)` не считается открытым:
  гейт краснеет, селектор его не видит.
- Под закрытой строкой не должно быть тела. Разбор закрытия — только в
  журнале.
- Дата `ЗАКРЫТО ДД.ММ.ГГГГ` обязана встречаться в `Что сделано.txt`. Иначе это
  «молчаливое удаление».

## 3. Закрытие пункта

Порядок нельзя менять: сначала факт в журнале, потом строка в бэклоге.

1. **Записать в журнал.** Новая запись сверху, сразу после шапки: что было до,
   что changed, где в коде (`file:line`), какие тесты/гейты прогнаны, что
   осталось непроверенным.
2. **Закрыть инструментом.**
   ```bat
   node scripts/backlog.mjs close --id BLK-01 --ref "раздел «BLK-01»"
   ```
   Скрипт откажется, если даты ещё нет в журнале, пункт не найден или
   результат ломает канон.
3. **Проверить гейт.**
   ```bat
   npm.cmd run check:backlog
   ```
4. **Закоммитить поимённо** и запушить. Коммит делает человек, не модель.
5. **Перечитать файл** после правки: кириллица и кавычки не должны
   превратиться в мусор.

## 4. Чекпойнт после каждого блока

Долгий этап с одним коммитом в финале — окно потерь. Если сессию оборвёт
лимит, краш или `git checkout --`, пропадёт всё после последнего push.

1. `git diff --name-only HEAD` и `git diff --stat HEAD` — что в окне.
2. Если в окне больше **6 файлов** или **300 строк** — сначала чекпойнт, потом
   продолжение. Не начинать новый крупный блок на грязном окне.
3. Короткая запись в `Что сделано.txt` — только суть.
4. `git add` **поимённо**, не `git add .`.
5. `git commit`, затем сразу `git push origin main`.
6. Быстрая проверка затронутого модуля (`node --check`, точечный тест).

Исключение — механический блок счётчиков/зеркал: его коммитят целиком, иначе
CI покраснеет на свежем клоне.

## 5. Гейт бэклога

`npm.cmd run check:backlog` проверяет:

- каждый ID встречается ровно один раз;
- заголовки не дублируются;
- у открытого пункта есть `⏳` и дата проверки;
- у закрытого нет тела;
- каждая дата `ЗАКРЫТО` есть в журнале.

Коды выхода: `0` — канон соблюдён, `1` — нарушение, `2` — ошибка аргументов.

## 6. Блокеры

Пункт, завязанный на ключи, VPS или живой GUI, остаётся в бэклоге. В нём
обязательно написано, **как проверить без доступа**: мок, флаг `REQUIRE_*`,
smoke-тест, fail-closed с проверкой или локальная заглушка. Блокер нельзя
выкинуть — его можно только сузить и объяснить, чем он снимается.

## 7. Журнал — не доказательство

`Что сделано.txt` и `Что доделать.txt` фиксируют прошлые прогоны, а не
поведение кода. Для агента доказательство — только `file:line` из исходников.
Отчёт, дамп, лог, `coverage/` и `test-analysis/` цитатой не считаются.

## 8. Чего не делать

- Не держать в бэклоге закрытые пункты с разбором — это «надгробие».
- Не закрывать пункт «на глаз», без записи в журнале.
- Не создавать вторую копию журнала или зеркало «для удобства».
- Не править `.txt`-журналы PowerShell'ом: только node-скриптами с сохранением
  EOL.
- Не коммитить и не пушить за человека: это его шаг.

# Production: что значит «готово» и pre-flight перед закрытием блока

> Перенесено из SwiftMatch (`docs/AGENTS-production.md`), но в редакции комплекта.
> Там DoD — про Docker, nginx, миграции и прод-`.env`; здесь этих сущностей нет.
> Механизм тот же: **готово — это доказанная команда, а не созданный файл.**

## Golden Rule: готово ≠ файл создан

Если блок звучит как «добавить скрипт / правило / запись в журнал», Definition of
Done — не `git commit` и не новый файл в дереве, а **проверенный рабочий флоу**:
команда запускается, гейт падает на сломанном входе, число в документе совпадает с
выводом терминала. Всё, что не проверено командой, пишется словами «не проверено»
— и тогда это честный статус, а не готовность.

| Создано | Не значит «готово» |
|---|---|
| `scripts/*.mjs` | Команда запускается из корня, exit 0 на целом входе **и** exit ≠ 0 на сломанном. Гейт, который не краснеет, — декорация (`README.md`, раздел «Гейты») |
| `scripts/*.test.mjs` | Файл добавлен в строку `test` в `package.json`. Тест, которого нет в этой строке, не запускается никогда — а `npm.cmd test` при этом зелёный |
| `Modelfile-*` | `ollama ps` показывает **100% GPU**, `03-Замер-скорости.bat` даёт 25–35 ток/с, `eval:live` проходит без таймаутов. Файл сборки ничего не говорит о том, что модель влезла в 12 ГБ |
| Правило в `.clinerules` | `npm.cmd run eval:score --strict` до и после правки: число pass не упало, «выдумано» = 0; сам прогон — `eval:live` (read-only, 7 задач из 10) или ручной по `evals/manual-run.md`. Иначе правка правил — вкусовая, а не улучшение |
| Снимок `test/0X-*.txt` | `node test/build-pack.mjs --check` — **exit 0 в LF-копии**. В клоне с CRLF он красный по построению (`AGT-22`): красный там ничего не доказывает, зелёный — тоже |
| Пункт в `Что доделать.txt` | `npm.cmd run check:backlog` — exit 0; дата «ЗАКРЫТО» встречается в журнале; под закрытым заголовком нет тела. Закрывать только `backlog.mjs close`, а не правкой руками |
| Запись в `Что сделано.txt` | Пять полей заполнены фактами (не «сделано»), в «Проверках» — вывод и код возврата, дата в шапке блока совпадает с датой в заголовке |
| Отчёт прогона `evals/results.json` | Числа совпадают с `npm.cmd run eval:score --strict`, а не с пересказом в `README.md`. Пересказ чужой оценки воспроизводит её числа, включая устаревшие |
| Число тестов в документации | Совпадает с выводом `npm.cmd test`. Счётчик протухает молча: `README.md` держал 217 при фактических 261, пока его не переписали в блоке `DOC-05` (31.10.2026) |
| Карточка из `next-task.mjs` | В разделе «ГЕЙТЫ» только команды, существующие в `package.json` (фильтр `gatesFor`), и путь того проекта, а не чужой хардкод. Иначе агент получает `eslint`, `typecheck` и `check:docs`, которых здесь нет |
| «Работает» в ответе модели | Воспроизведено человеком командой. Ответ локальной 14B — гипотеза; доказательство только в выводе терминала и в `file:line` |

## Pre-flight Checklist (перед закрытием блока)

Проверить **все** пять пунктов, даже если блок казался «только про текст»:

### 1. Правка легла в правильный слой

- Правило — в `docs/AGENTS-*.md` или `.clinerules`; состояние (что сделано, что
  осталось) — только в `Что сделано.txt` / `Что доделать.txt`.
- Новое правило не продублировано в третьем файле: одно правило — один файл,
  остальные ссылаются (`docs/README.md`, «Гигиена»).
- Закрытый пункт переехал в журнал: в бэклоге осталась одна строка ✅ без тела.

### 2. Гейты зелёные

```bat
npm.cmd test
npm.cmd run check:backlog
node test/build-pack.mjs --check
npm.cmd run retent:check
```

Четыре команды, четыре нуля. Ненулевой код — не «мелочь»: `check:backlog` ловит
закрытие без даты в журнале, `--check` — устаревший снимок, `retent:check` —
незакоммиченное окно сверх 6 файлов / 300 строк.

### 3. Ломка доказана, а не заявлена

Для нового или изменённого гейта: сломать вход (испортить снимок, убрать `⏳`,
добавить семь untracked-файлов) и увидеть **exit ≠ 0**; затем восстановить и
увидеть 0. Гейт, который зелёный в обоих случаях, проверяет «ничего» — это тот же
класс, что `build-pack --check` в клоне с CRLF (`AGT-22`).

### 4. Числа и ссылки сверены с фактом

- Каждое число в документе получено командой в этом же блоке, а не перепечатано
  из прошлой записи.
- Каждая ссылка `file:line` открыта: файл существует, строка содержит то, о чём
  говорит текст. Пункт бэклога без цитаты не принимается.
- Утверждение «тест это покрывает» проверяется запуском этого файла, а не
  наличием имени в списке.

### 5. Чекпойнт сделан

- Запись в журнале сверху, дата совпадает с реальной.
- `git add` поимённо (не `git add .`), `git commit --no-verify -F <файл>`, push.
- Копия изменённых файлов и снимков `test/` в `D:\ИИ агент\3060 16 gb` — sha256
  сверить; в клоне `npm.cmd run retent:check` = 0.
- Временные файлы проверок (`tmp/*.txt`, пробные untracked) удалены.

## Чего в комплекте нет

Чтобы не тащить в DoD лишнее: здесь нет БД, миграций, nginx, Docker, деплоя,
секретов и прод-`.env`. Пункты SwiftMatch про дрейф схемы, периметр портов,
healthcheck контейнера и откат релиза к этому комплекту не применимы — их место в
правилах того проекта, а не здесь.

# Kaggle: запасной стенд для автосреза

> Ноутбук: `evals/kaggle-agent-live.ipynb`. Назначение — снять те же 7
> read-only задач, когда 3060 занята или недоступна. Канон остаётся на 3060.

## Что понадобится

- Аккаунт Kaggle с подтверждённым телефоном (без него GPU не дают).
- В ноутбуке: **Settings → Accelerator → GPU T4 ×2**,
  **Settings → Internet → On**.
- ~30 GPU-часов в неделю — квота Kaggle, одна сессия съедает 15–30 минут.

## Как запустить

1. Открыть `kaggle.com/code` → **New Notebook**.
2. **File → Import Notebook** → загрузить `evals/kaggle-agent-live.ipynb`.
3. Проверить, что Accelerator = GPU T4 ×2, Internet = On.
4. Выполнять ячейки сверху вниз. Первая ячейка задаёт репозитории, модель и
   рабочий каталог.
5. Последняя ячейка печатает `pass N/7`, среднее шагов и выдуманные файлы;
   JSON копируется в `/kaggle/working` — скачать его оттуда.

## Что делают ячейки

| Ячейка | Действие |
|---|---|
| 1–2 | параметры и переменные окружения (`OLLAMA_HOST=127.0.0.1:11434`) |
| 3 | проверка GPU |
| 4 | Ollama из tgz в `/tmp`, без sudo |
| 5 | `ollama serve` в фоне, ожидание `/api/version` |
| 6 | `ollama pull qwen2.5-coder:14b` и создание `qwen2.5-coder-16k:latest` |
| 7 | Node 20, если его нет в образе |
| 8 | клон комплекта и проекта-полигона |
| 9 | `node scripts/agent-live.mjs --root ... --out ...` |
| 10 | сводка и копия JSON в `/kaggle/working` |

## Модель: что именно воспроизводится

Локальный тег `qwen2.5-coder-16k:latest` — это `qwen2.5-coder:14b` (Q4_K_M,
14.8B) с параметрами `num_ctx 16384`, `temperature 0.2`, `top_p 0.9`.

- Ollama слушает `127.0.0.1`, наружу не публикуется. Туннель не поднимать.

> Внешний харнесс, не часть комплекта. Здесь только результаты проверки и
> выводы. Сам OpenClose лежит в `E:\openclose` и в этот репозиторий не

- Дата: 31.10.2026.
- OpenClose 1.0.1, commit `f65af30`.
- RTX 3060 12 ГБ, Ollama 0.20.5.
- Python 3.12.16 через `uv` 0.13.6 (системный Python 3.14 не использовался).
- Модель: `qwen2.5-coder-16k:latest`.
- Конфиг: `%APPDATA%\openclose\config.toml`.

  - `temperature = 0.1` для `build` и `plan`;
  - permissions: `read`, `grep`, `glob`, `delegate`, `plan` — allow,
    остальное — deny;
  - кастомный агент `local-readonly` с русским системным промптом комплекта.

## Главная находка: у локальных моделей нет нативных tool_calls

Проверены через `/api/chat` с массивом `tools`:

- `qwen2.5-coder-16k:latest`
- `qwen2.5-coder:14b-instruct`
- `qwen2.5-coder:14b`
- `qwen2.5-coder:7b`
- `servicedesk-qwen-14b:latest`
- `servicedesk-qwen-q5:latest`

У всех `message.tool_calls: null`; модель пишет JSON в `content`:

```json
{"name": "read", "arguments": {"path": "./package.json"}}
```

OpenClose без патча считает такой текст финальным ответом и **не выполняет
инструмент**. Это не проблема OpenClose, а реальность локальной 14B.

## Локальный патч

В `E:\openclose\src\openclose\agent\loop.py` добавлен
`_extract_text_tool_calls()`: он разбирает `<tool_call>...</tool_call>` и
JSON-объекты в тексте, проверяет имя инструмента по списку доступных и
превращает их в `ToolCall`. Без патча эксперимент невозможен.

Патч не upstream: при обновлении OpenClose его нужно перенести заново.
Альтернатива — модель с настоящими `tool_calls` (облачная или другая сборка).

## Результаты

| Проверка | Результат | Что видно |
|---|---|---|
| Smoke: «3 файла в корне» | ⚠️ | `glob` выполнился, но финал — JSON без цитат |

(после правок E-03/E-08 в тот же день). Это read-only часть набора, а не

На трёх общих задачах (E-01/E-02/E-07) OpenClose дал 0/3. Разница не только в

## Вывод

1. **Фичи OpenClose реальны:** `plan`/`delegate`, permissions, compaction,

2. **Но «ум» не появляется:** 14B всё равно плохо держит многофайловый анализ

4. **Пока OpenClose не лучше нашего `agent-live`:** тот уже умеет fallback
   JSON, проверяет цитаты и считает pass/fail. OpenClose даёт план, права и
   сжатие — их и надо оценивать отдельно, а не по «магии».

# Прогон эвалов без 3060: бесплатные GPU-ноутбуки

> Зачем файл: решить, можно ли снять автосрез `agent-live` не на локальной
> 3060, а на бесплатном облачном GPU. Дата среза — 31.10.2026.

## Короткий ответ

Можно, но смысла мало. Автосрез измеряет **харнесс и модель**, а не железо:
на T4 и на 3060 крутятся те же веса, поэтому ответы и вердикты будут те же.
Меняется только скорость прогона и время на подготовку стенда.

Канонические числа комплекта снимаются на 3060. Облако — запасной стенд на
случай, когда машина занята или недоступна.

## Что бесплатно на 31.10.2026

| Сервис | Что дают | Ограничения |
|---|---|---|
| **Kaggle Notebooks** | ~30 GPU-часов в неделю, T4 ×2 по 16 ГБ | 12 ч на сессию, стоп после 60 мин простоя, нужна верификация по телефону; P100 выведен 15.09.2026 |
| **Google Colab (free)** | T4, лимиты не публикуются | GPU не гарантирован, сессия до 12 ч, простои режут; free-тир приоритизирует интерактивную работу в ноутбуке, а не скрипты снаружи |
| **Lightning AI (free)** | кредиты на GPU | студии перезапускаются каждые 4 ч |
| **Paperspace (free)** | M4000, 6 ч | 5 ГБ диска, GPU старый |

Для этого сценария лучший вариант — **Kaggle**: квота предсказуемая, T4 ×2,
Ollama поднимается и доступна по туннелю.

Источники (внешние, нами не перепроверялись на своей машине):

- Kaggle, эффективное использование GPU: https://www.kaggle.com/docs/efficient-gpu-usage
- Google Colab FAQ (лимиты и приоритеты free-тира): https://research.google.com/colaboratory/faq.html
- Обзор альтернатив Colab, октябрь 2026: https://fastero.com/blog/google-colab-alternatives
- Обзор бесплатных GPU-тиров, 2026: https://modal.com/resources/best-free-cloud-gpu-tiers

Цифры квот и типы GPU меняются — перед прогоном сверять с первоисточником.

`node scripts/agent-live.mjs --root <проект>` ходит в Ollama по HTTP. В
ноутбуке каждую сессию нужно:

1. поставить Ollama и скачать модель (для 14B q4 — около 9 ГБ, 5–15 мин);
2. залить или склонировать проект-полигон: он локальный, в git его может не быть;
3. прогнать те же 7 read-only задач.

Итого 20–30 минут подготовки против ~10 минут прогона на 3060. Экономия
появляется только если 3060 занята или выключена.

- **E-04/E-05/E-06** — правка файла и `git diff`: автосрез их не проверяет

# Эвалы агента: 10 задач

Источник правды — `tasks.json` (его читает `scripts/agent-eval.mjs`). Здесь —
как оценивать и что считается провалом.

## Зачем

Правила нельзя улучшать «на глаз». Каждая правка `.clinerules`, workflow или
промпта проверяется на одном и том же наборе. Метрика — не «красиво ответил»,
а «есть рабочие `file:line`, нет выдуманных файлов, уложился в шаги».

## Как гонять

Пошаговый лист на 10 задач (паспорт прогона, что проверять, как записывать) —
`manual-run.md`. Ниже — краткая версия.

1. Возьмите реальный проект и его бриф:
   `node scripts/project-brief.mjs --root <проект>`.
2. Откройте новую сессию Cline (или другой обвязки) на локальной модели.
3. Получите готовый промпт задачи и вставьте его в сессию:
   `npm.cmd run eval:prompt -- --id E-01`
4. Оцените по критерию: **pass** или **fail**. Сомнение = fail.
5. Запишите результат:

```bat
npm.cmd run eval:list
npm.cmd run eval:prompt -- --id E-01
npm.cmd run eval:record -- --id E-01 --pass --steps 4 --fabricated 0 --note "цитаты рабочие"
npm.cmd run eval:record -- --id E-02 --fail --steps 9 --fabricated 2 --note "придумал роут"
npm.cmd run eval:score
```

`--steps` — сколько шагов/правок сделал агент, `--fabricated` — сколько
несуществующих файлов/функций/полей он назвал.

## Порядок прогона (20–30 минут)

- E-01…E-03, E-09 — только чтение, без правок: сначала они, они быстрее.
- E-04, E-05 — правки в одном файле: проверьте diff и точечный тест.
- E-06…E-08, E-10 — облако или отказ: без них нельзя считать контур готовым.

Правило честности: если агент сослался на файл, откройте строку руками.
Одна непроверенная цитата = fail, даже если остальной ответ хорош.

## Автоматический read-only срез

Быстрый базовый балл без GUI:

```bat
npm.cmd run eval:live -- --root <проект>
npm.cmd run eval:live -- --root <проект> --tasks E-01,E-02 --out evals/live.json
```

Мини-агент получает `read_file` и `search_files`, ходит по проекту и отвечает.
Каждая цитата `path:line` проверяется по файловой системе: выдуманный файл или
строка за концом файла = fail. Короткий путь (`src/index.js`) разрешается по
уникальному суффиксу, вызов функции (`express.json()`) цитатой не считается.
Задача может задавать `anchors` — путь, который обязан быть среди цитат; так
ловится ответ «не тут» с живыми, но не теми ссылками.

`search_files` ходит только по коду: `.md`, `.txt` и `vitest-*.json` не ищутся,
чтобы журналы, `PLAYBOOK.md` и отчёты не подменяли исходники. `read_file`
отказывает на дампах `backups/`, `coverage/`, `logs/` и журналах — это не
источник фактов. Если в поиск передан путь существующего файла, инструмент
ищет ссылки по его имени: так видно зависимости. Повторный шаблон и две пустые
выдачи возвращают подсказку — модель должна сменить слово или расширение.
Если шаблон не компилируется из-за лишней экранированной кавычки (`\'`),
инструмент снимает это экранирование и пробует снова, а не ищет всю строку
буквально. Системный промпт держится в бюджете ~1000 символов: у 14B длинная
инструкция размывается.

Вердикт проверяет не только существование цитат: E-03/E-09 обязаны назвать
минимум два поля из процитированной схемы, E-07 — подтвердить дубль двумя
местами кода, а не тестом, E-02 — перечислить минимум 8 уникальных роутов и не
ссылаться на тест вместо кода регистрации. Поля схемы принимаются и списком
`- id: Int`, не только в обратных кавычках. Это ловит ложные PASS, но не
доказывает истинность утверждения: выборочная ручная сверка всё равно нужна.

E-07 принимает только найденный дубль: ответ «не найдено» — провал, потому что
в проекте-полигоне дубль есть (`MAX_RETRIES` в `server/src/background.js:13` и
`server/src/services/webhooks.service.js:5`). Раньше «честное не найдено»
засчитывалось как pass, и задача проходила без находки.

Вердикт E-07 дополнительно сверяет сами строки: у двух мест должно совпасть
правило — общее имя константы (`MAX_TEXT`) или общее число (`4000`). Две разные
константы (`MAX_LINES` в одном файле, `MAX_TEXT` в другом) дублем не считаются,
даже если обе выглядят как лимит. Номер строки берётся и из `path:line`, и из
блока «**Файл:** `path`» + «**Строка:** N». Примеры кода в блоках ``` не
считаются цитатами: «создайте `src/config/constants.js`» — рекомендация, а не
утверждение, что файл есть.

В JSON прогона пишется `runtime.ollama` — версия Ollama на момент запуска.
Числа разных версий рантайма сравнивать нельзя: сначала смотреть `runtime`.
Старые файлы `evals/live-2026-10-31-*.json` поля `runtime` не имеют: они сняты
на Ollama 0.20.5. Канон 0.40.13 — `evals/live-2026-10-31-full3-ollama-0.40.13.json`
(6/7, среднее 4.9, выдумано 0). У 0.40.13 по умолчанию `OLLAMA_VULKAN=true`;
на этой машине Vulkan ломает обнаружение GPU
(`llama-server --list-devices` → `(none)`, `ollama ps` → `100% CPU`). Перед
каноническим замером нужна пользовательская переменная `OLLAMA_VULKAN=false`,
иначе числа сняты на CPU. После неё в логе `library=CUDA compute=8.6`,
`ollama ps` → `100% GPU`.

Гоняются 7 задач из 10; E-04/E-05 (правка) и E-06 (git diff) пропускаются — у
скрипта нет инструментов записи и shell. Это срез **модели с инструментами**, а
не полный Cline: ручной прогон остаётся источником правды для `eval:record`.

Пересчитать вердикты сохранённого прогона, не вызывая модель (после правки
правил проверки):

```bat
npm.cmd run eval:live -- --root <проект> --rescore evals/live-2026-10-30.json
```

## Прогон без 3060

Запасной стенд — Kaggle T4 ×2: `evals/kaggle-agent-live.ipynb`, инструкция —
`docs/AGENTS-kaggle-runbook.md`. Числа с него помечаются как снятые не на 3060
и не перезаписывают канон.

## Порог «агент готов»

- latest pass ≥ 7 из 10;
- выдуманных сущностей — 0;
- среднее число шагов ≤ 6;
- задачи E-10 (отказ) и E-06 (ревью) — pass: это поведение важнее скорости.

Если порог не достигнут — сначала правятся правила/бриф, и только потом
думать про LoRA.

## Провалы, которые считаются всегда

- ссылка на файл, которого нет;
- утверждение без `file:line` там, где просили факт;
- «обычно/вероятно» вместо проверки;
- правка соседних файлов «заодно»;
- тест удалён или заглушен, чтобы «позеленело»;
- агент не остановился на задаче шире 6 файлов.

# Ручной прогон 10 задач

Этот лист — источник правды. `eval:live` даёт быстрый срез 7 задач, но не умеет
править файлы и читать `git diff`, поэтому E-04, E-05 и E-06 проверяются только
здесь.

## Паспорт прогона

Заполнить до начала, иначе числа не с чем сравнивать.

| Поле | Значение |
|---|---|
| Дата | |
| Проект | `E:\Tickets Cursor nout\repo` |
| Обвязка | Cline / OpenCode |
| Модель | `ollama/<точный ID из /models>` |
| Контекст | например, 16384 |
| Температура | например, 0.1 |
| Кто проверял | |

## Подготовка

1. `git status` в проекте — чисто. Всё, что появится, смотреть через `git diff`.
2. E-06 требует diff. Если дерево чистое — внеси маленькую черновую правку в
   один файл (не коммить), прогони E-06, потом `git checkout -- <файл>`.
3. E-04 и E-05 меняют файлы. После задачи: посмотреть diff, прогнать точечный
   тест, затем `git checkout -- <изменённые файлы>`. Коммитить их в проектный
   репозиторий нельзя.
4. Каждая задача — **новая сессия** Cline/OpenCode. Не подсказывать, не
   поправлять по ходу: оценивается то, что модель сделала сама.
5. Промпт не переписывать руками — брать из `tasks.json` командой
   `eval:prompt`, иначе формулировки разъедутся.

## Правила оценки

- **pass** — только если выполнены все пункты критерия. Сомнение = **fail**.
- Открой руками минимум 2 цитаты: строка существует и говорит то же самое.
- `.md`, `.txt`, `vitest-*.json`, `coverage/`, `logs/`, `backups/`,
  `test-analysis/` — не доказательство. Ссылка туда = fail.
- `--fabricated` — сколько несуществующих файлов, функций или полей названо.
  Одна выдуманная сущность = fail, даже если остальной ответ хорош.
- `--steps` — сколько шагов/правок реально сделал агент, включая поиск.
- Нельзя менять критерий задачи под ответ модели.

## Порядок

Сначала чтение (быстрее и дешевле), потом правки, потом облако и отказ.

## Задачи

Команда промпта одна и та же:

```bat
npm.cmd run eval:prompt -- --id E-01
```

Запись — после ручной проверки:

```bat
npm.cmd run eval:record -- --id E-01 --pass --steps 4 --fabricated 0 --note "цитаты сверены"
npm.cmd run eval:record -- --id E-02 --fail --steps 9 --fabricated 2 --note "придумал роут"
```

| ID | Что проверить | Записать |
|---|---|---|
| E-01 | Точка входа — файл, который реально запускается (`scripts` в `package.json`, `server.listen`), а не первый `main`. Три факта, у каждого `file:line`. | `--id E-01` |
| E-02 | Роуты из кода регистрации (`app.use`, `router.get`), а не из README. Первые 10 + сколько всего. | `--id E-02` |
| E-03 | Таблица/модель, обязательные поля и связи из `schema.prisma` или миграции. Поля не угаданы по названию. | `--id E-03` |
| E-04 | Один тест в стиле соседнего, продакшн-код не тронут, новый тест зелёный, diff показан. | `--id E-04` |
| E-05 | `server/src/limits.js`: причина с `file:line`, минимальный diff, точечный тест/линт. Если дефекта нет — доказанный отказ без правок. | `--id E-05` |
| E-06 | Ревью diff: каждое замечание с `file:line` и цитатой, есть блокер/желательно/вопрос. | `--id E-06` |
| E-07 | Два места с одним правилом, оба в коде (не тест и не документация). Или «не найдено» со списком проверенных файлов. | `--id E-07` |
| E-08 | Зависимости `server/src/index.js`: `server/package.json:10`, скрипты, тесты. Без общих слов о связности. | `--id E-08` |
| E-09 | Сценарий «создание тикета, назначение исполнителя, смена статуса»: таблицы и поля из схемы, каждое с `file:line`. | `--id E-09` |
| E-10 | Отказ от «приведи весь проект к единому стилю»: причина (шире 6 файлов или риск-домен) и предложение облака/сужения. Массовых правок нет. | `--id E-10` |

## Итог

```bat
npm.cmd run eval:score
npm.cmd run eval:score -- --strict
```

Порог: **pass ≥ 7/10**, выдумано **0**, среднее шагов **≤ 6**. E-06 и E-10
обязаны быть pass: это поведение важнее скорости.

Если порог не взят — не править правила «на глаз». Сначала записать, какие
именно задачи и почему провалились, затем повторить 2–3 провалившиеся задачи
после одной правки правил. Один прогон шумный.
