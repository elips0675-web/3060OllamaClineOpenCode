# SwiftMatch — жёсткие правила для ИИ-агента (Cline / Roo Code)

> **Это пример правил, а не правила комплекта.** Так выглядит `.clinerules`
> реального проекта (React + Express + MySQL), из которого собран комплект;
> `README.md:45` называет файл «копией проектного». Правила для нового проекта
> ставит `scripts/init-project.mjs`: `templates/rules/00-project.md`,
> `templates/agent-protocol.md`, `templates/workflows/`, `templates/few-shot.md`.
>
> Команды в п. 3, 4 и 7 относятся к тому проекту. В комплекте работают только:
> `npm.cmd test`, `npm.cmd run check:backlog`, `node test/build-pack.mjs --check`
> и `node scripts/next-task.mjs`. Скриптов `typecheck`, `check:docs`,
> `check:n-plus-one`, `check:enum-constraints`, `check:prod-mock`, `check:mirrors`
> и инструментов `eslint`/`vite` в нём нет: `package.json` объявляет `test*`,
> `check:backlog`, `backlog:*`, `eval:*`, `init:project`, а `devDependencies` —
> только `vitest`. Пропущенные команды в карточку задачи не попадают:
> `gatesFor` (`scripts/next-task.mjs`) отбрасывает гейт, которого нет в
> `package.json`.

Проект: React 18 + TS strict + Tailwind v3 + shadcn/ui + Vite (front 8081), Express (API 3002),
MySQL 3306, Redis (опционально, in-memory fallback), Socket.IO, Capacitor Android.
Канон правил автора: AGENTS.md + docs/AGENTS-*.md. Бэклог задач: «Что доделать.txt».
Пакет для внешнего ИИ: `test/` — собирается `node test/build-pack.mjs`, проверяется `--check`.

## 1. Работать только из бэклога
Перед любым действием открой «Что доделать.txt» и возьми задачу по ID (QA-01, COV-02, SRCH-01 …).
Никакого «рефакторинга заодно», никаких придуманных задач. Одна задача = один микроблок = один коммит.
Пункт без `file:line` не считается фактом: открывай файл и строку, а не пересказывай.

## 2. Терминал на этой машине: npm.cmd / npx.cmd
PowerShell блокирует npm.ps1 и npx.ps1 (ExecutionPolicy). Поэтому в PowerShell:
`npm.cmd run <script>`, `npx.cmd <tool>`.
В «Command Prompt» и Git Bash обычные `npm` / `npx` работают.

## 3. Зелёный минимум перед словом «готово» (все exit 0)

Показать вывод команд в отчёте. Не перекладывать починку линтера на пользователя.

## 4. Зеркала test/ — только скриптом

Синхронизация: `node scripts/check-doc-mirrors.mjs --fix`

## 11. Локально или в облако

Локальная модель (14B на 3060): одна правка в одном файле, объяснение файла,
мелкий рефакторинг. Облако: больше одного файла, SQL/схема, разбор красных
гейтов, ревью диффа, тесты на 200+ строк.
Локальная ошиблась дважды — скажи «нужна эскалация в облако» и остановись,
не продолжай наугад.

### 11.1 Кто делает коммит

Пункт 7 (чекпойнт) описывает порядок коммита, но исполнитель — не локальная
модель. Локальный агент (14B на 3060) НЕ выполняет `git add`, `git commit`
и `git push`: после правки он показывает дифф, вывод гейтов и точный список
файлов, а коммит делает человек. Причина: 14B не прогоняет полный набор
гейтов надёжно, а ошибка в сообщении коммита или в составе файлов уходит
в `main` без ревью.

Облачный агент коммитит только по прямому указанию человека в текущей сессии;
без такого указания — тоже готовит изменения и останавливается.
Запрет из пункта 6 (`git reset --hard`, `git checkout -- <файл>`) действует
для всех моделей без исключений.

## 12. Агентный цикл: порядок шага

Правила запрещают плохое, но не задают хороший цикл. Порядок обязателен:

1. **RESTATE** — одной строкой: что просят и что считается готовым.
2. **MAP** — карта проекта (`project-brief`), затем точечный поиск. Не читать
   репозиторий целиком.
3. **PLAN** — не больше 3 шагов, один файл на шаг. Показать план до правки.
4. **ACT** — одна правка за шаг, минимальный дифф.
5. **VERIFY** — линт/типы/тест, прочитать вывод целиком, а не первую строку.
6. **REPORT** — что изменено (`file:line`), что проверено, что нет.

Бюджет: ≤ 2 поисков и ≤ 6 чтений на задачу, 1 правка на шаг. Две неудачи
подряд — стоп с причиной и гипотезами, а не «долбить» правку.

Поиск и доказательства (правила из живого прогона 30.10.2026):

- Поиск построчный: шаблон с `{...}` или `[^)]*` на несколько строк не найдёт
  ничего. Две пустые выдачи подряд — менять слово или расширение.
- Точка входа — файл, который реально запускается (`scripts` в `package.json`,
  `server.listen`), а не первое совпадение `main`.
- «X зависит от Y» подтверждается чтением X (импорт, скрипт, конфиг), а не
  догадкой по имени файла.
- «Не найдено» без списка проверенных файлов — не ответ.
- Факты о схеме БД — из `.prisma` или `.sql`; `.md` доказательством не является.
- Журналы (`Что сделано.txt`, `Что доделать.txt`), `context.txt`, отчёты
  `vitest-*.json`, `coverage/`, `test-analysis/` — не источник фактов о коде.

Полный протокол — `templates/agent-protocol.md`. Процедуры (`brief`, `fix`,
`test`, `review`, `refactor`) — `templates/workflows/`; в проекте они лежат в
`.clinerules/workflows/` и вызываются как `/brief.md`. Память между сессиями —
`templates/cline_docs/` (в проекте — `cline_docs/`). Проверка —
`templates/verify-checklist.md`.

Если в проекте `.clinerules` — каталог (00-role, 10-gates, 20-workflow,
30-context-map), цикл кладётся отдельным файлом `40-agent-cycle.md`, а не
переписывает существующие правила.

Измеримость: `evals/tasks.json` + `scripts/agent-eval.mjs`. Порог «агент
готов» — pass ≥ 7/10, выдумано 0, среднее шагов ≤ 6. Ниже порога правятся
правила, а не веса.

Источник фактов — только исходный код. Отчёты тестов (`vitest-*.json`),
coverage, логи и `test-analysis/` доказательством не являются.

## Агентный цикл (блок для проектного .clinerules)

Правила держать короткими: 14B теряет длинный системный текст. Процедуры —
в `.clinerules/workflows/`, а не здесь.

### Цикл одного шага

1. **RESTATE** — одной строкой: что просят и что считается готовым.
2. **MAP** — `project-brief`, затем `search_files`. Не читать репозиторий целиком.
3. **PLAN** — не больше 3 шагов, один файл на шаг. Показать план до правки.
4. **ACT** — одна правка за шаг, минимальный diff.
5. **VERIFY** — линт/типы/точечный тест. Прочитать вывод, а не предположить.
6. **REPORT** — что изменено, `file:line`, что осталось непроверенным.

### Бюджет

- ≤ 2 поисков и ≤ 6 чтений файлов на одну задачу.
- 1 правка на шаг; не «заодно» рефакторить соседние файлы.
- Вывод команды — только хвост/ошибки, не вся простыня.
- Контекст: если прочитано > 6 файлов — остановиться и пересобрать карту.

### Уверенность

Перед первым инструментом — оценка 0–10: понял задачу и нашёл правильный файл.

- 7–10 → действуй по циклу.
- 4–6 → один уточняющий вопрос, без правки.
- 0–3 → стоп: перечисли, чего не хватает, и предложи облако.

Уверенность не заменяет проверку: она лишь запрещает править наугад.
Примеры правильного ответа и вызова инструмента — `50-few-shot.md`.
План до правок — workflow `/deep-planning`.

### Стоп-правила

- Две неудачные попытки подряд → стоп, показать причину, предложить облако.
- Нужен файл, которого нет в брифе и который не открывался → не утверждать, что он есть.
- Вопрос про деньги, доступы, схему БД, деплой → облако, даже если файл один.
- Для ответа нужно > 6 файлов → облако, а не «дочитать как-нибудь».

### Формат ответа

- Сначала «Вывод» — 2–4 строки.
- Затем «Факты» — список с `file:line` и короткой цитатой.
- Затем «Не проверено».
- Затем «Следующий шаг» — один.

### Поиск и доказательства

- Поиск построчный: `{...}` и `[^)]*` на несколько строк ничего не найдут.
  Две пустые выдачи подряд → менять слово или расширение, не повторять шаблон.
- Точка входа — файл, который реально запускается (`scripts` в `package.json`,
  `server.listen`), а не первое совпадение `main`.
- «X зависит от Y» подтверждается чтением X, а не догадкой по имени файла.
- «Не найдено» без списка проверенных файлов — не ответ.
- Схема БД — только `.prisma` или `.sql`; `.md` доказательством не является.
- Журналы, `context.txt`, отчёты `vitest-*.json`, `coverage/` и
  `test-analysis/` — не источник фактов о коде: это результат прошлого прогона.

### Запреты

- Не выдумывать файлы, функции и поля по названию.
- Не использовать отчёты тестов, coverage, логи и `test-analysis/` как
  доказательство: источник фактов — исходный код.
- Не писать «обычно», «вероятно», «как правило» без пометки «догадка».
- Не делать `git add/commit/push` — это делает человек.
- Не отключать линтер/тест, чтобы «позеленело».

# 50 — Примеры правильного ответа

> Два-три примера работают лучше длинного списка запретов. Пути условные:
> это формат, а не факт о конкретном проекте. Перед инструментом оцени
> уверенность 0–10; ниже 7 — задай вопрос, а не правь.

## Пример 1. Факт с цитатой, а не пересказ

Задача: «Где монтируются роуты API?»

Плохо:

```text
Роуты лежат в app.js, там подключаются все модули.
```

Хорошо:

```text
Вывод: роуты монтируются в server/src/app.js, до обработчика ошибок.

Факты:
- `server/src/app.js:143` — `app.use('/api/auth', authRoutes);`
- `server/src/app.js:151` — `app.use('/api/tickets', ticketsRoutes);`

Не проверено: порядок middleware выше строки 140.
Следующий шаг: прочитать `server/src/app.js:120-170`.
```

## Пример 2. Сначала поиск, потом чтение

Задача: «Где задан лимит повторов?»

```json
{"name":"search_files","arguments":{"pattern":"MAX_RETRIES","glob":"js"}}
```

После выдачи — точечное чтение, а не чтение всего файла:

```json
{"name":"read_file","arguments":{"path":"server/src/background.js","start":1,"end":30}}
```

Плохо: сразу читать `server/src/background.js` целиком «на всякий случай».
Хорошо: поиск по имени, затем 20–30 строк вокруг совпадения.

## Пример 3. Честное «не найдено»

```text
Вывод: в проверенных файлах поле `assignee_id` не найдено.

Проверено:
- `server/prisma/schema.prisma`
- `server/src/routes/tickets.js`

Не найдено: `assignee_id`, `assigneeId`.
Следующий шаг: уточнить, как в проекте называется исполнитель.
```

Плохо: «поле, вероятно, называется `user_id`» без чтения схемы.

# Чек-лист проверки (для агента и человека)

Скопировать в проект и заменить команды на свои. Проверка — часть шага, а не
финальная формальность: без неё «готово» ничего не значит.

## Перед правкой

- [ ] Понятно, какой файл меняем и почему (есть `file:line` причины).
- [ ] Правка не выходит за один файл; соседние файлы — отдельный шаг.
- [ ] Известно, какая команда подтвердит результат.
- [ ] Риск-домен проверен: деньги / доступы / БД / деплой → облако.

## После правки

- [ ] Прочитан diff: нет случайных удалений, отладки и закомментированного кода.
- [ ] Линт по изменённому файлу — 0 ошибок.
- [ ] Типы — без новых ошибок (если есть typecheck).
- [ ] Точечный тест — зелёный; если теста не было — добавлен или записано «не покрыто».
- [ ] Полный прогон гейтов — только если правка затрагивает общий контур.
- [ ] Вывод команды прочитан целиком, а не первая строка.
- [ ] В отчёте названо, что осталось непроверенным.

## Команды-заготовки (заменить на проектные)

В комплекте работают эти:

```bat
npm.cmd test
npm.cmd run check:backlog
node test/build-pack.mjs --check
```

В проекте-образце (SwiftMatch) к ним добавляются `npx.cmd eslint <файл>`,
`npm.cmd run typecheck`, `npm.cmd test -- <точечный тест>`, `npm.cmd run check:docs`,
`npx.cmd vite build` — они ставятся вместе с проектом, в комплекте этих скриптов
и инструментов нет. Проверять надо те, что есть в `package.json` проекта, а не
список выше.

## Признаки «зелено»

- команда завершилась с кодом 0;
- в выводе нет новых `error`, `FAIL`, `✗`;
- предупреждения не выросли (лучше — не изменились);
- изменённый файл действительно попал в проверку, а не был пропущен фильтром.

## Если упало

1. Прочитать ошибку целиком и назвать строку.
2. Одна попытка исправления — по причине, а не «наугад».
3. Вторая неудача → стоп: показать ошибку, гипотезу и что уже пробовали.
4. Не удалять тест, не глушить линтер, не расширять `any`, чтобы «позеленело».

2. Прочитай файл целиком; назови, что именно упрощаем и зачем.
3. Составь план из 1–3 шагов, без изменения публичного контракта.
4. Делай по одному шагу, после каждого — тесты.
5. Если поведение изменилось — откати шаг и объясни почему.
6. Отчёт: что упрощено, тесты до/после, что не проверено.

## Стоп

- Нет тестов на участок → сначала `/test`, потом рефакторинг.
- Файл больше 500 строк или правка затрагивает > 3 файлов → облако.

## Запреты

- Не менять API, схему БД и тексты ошибок без отдельного решения.
- Не смешивать рефакторинг и новую функциональность в одном шаге.

# /deep-planning — план до правок

## Когда

- Задача затрагивает больше одного файла.
- Неясно, где причина бага, или есть несколько вариантов решения.
- Правка риск-домена: деньги, доступы, схема БД, миграции, деплой.

Для одной очевидной правки в одном файле этот workflow не нужен.

## Шаги

1. **RESTATE** — одной строкой: что просят и что считается готовым.
2. **FACTS** — собери карту: `node scripts/project-brief.mjs --root .`.
   Выбери 3–6 файлов: точка входа → роуты → схема → тест.
3. **READ** — прочитай выбранные файлы целиком. Каждый факт — `file:line`
   и короткая цитата. Не пересказывай README.
4. **PLAN** — запиши `implementation_plan.md` по шаблону ниже. Не больше
   3 шагов, один файл на шаг.
5. **ASK** — если уверенность ниже 7/10, есть конфликт правил или риск-домен,
   остановись и задай вопрос. Без ответа не правь.
6. **ACT** — только после «делай»: одна правка за шаг, минимальный diff.
7. **VERIFY** — линт/типы/точечный тест. Прочитай вывод целиком.
8. **REPORT** — что изменено, `file:line`, что не проверено, следующий шаг.

## Шаблон implementation_plan.md

```markdown
# План: <короткое название>

## Цель
<что должно измениться в поведении>

## Факты
- `path:line` — цитата, что именно подтверждает.

## Шаги
1. <файл> — <правка> — <как проверить>
2. <файл> — <правка> — <как проверить>

## Риски
- <что может сломаться>

## Проверка
- <команда> → <ожидаемый результат>

## Открытые вопросы
- <вопрос человеку, если есть>
```

## Стоп

- Для плана нужно больше 6 файлов → облако, а не «дочитать как-нибудь».
- Риск-домен или миграция → облако + человек, даже если файл один.
- Две неудачные попытки подряд → стоп, показать причину и гипотезы.
- План не утверждён человеком → правок нет.

## Выход

`implementation_plan.md` в корне проекта (или в `tmp/`, если проект не хранит
планы) + один вопрос, если он есть. После утверждения — обычный цикл
`ACT → VERIFY → REPORT` из `40-agent-cycle.md`.

# /eval — измерить агента, а не поверить в него

## Когда

После правки правил, промптов или смены модели. Задача — получить число, а не
впечатление «вроде стало лучше».

## Шаги

1. Автоматический срез (7 из 10 задач, read-only):
   `npm.cmd run eval:live -- --root <проект> --out evals/live-<дата>.json`
2. Прочитать таблицу: `pass`, шаги, выдуманные файлы, причину fail.
3. Ручной прогон оставшихся задач в Cline: `npm.cmd run eval:prompt -- --id E-04`.
4. Записать каждый результат: `npm.cmd run eval:record -- --id E-04 --pass|--fail
   --steps N --fabricated N --note "…"`.
5. Порог: `npm.cmd run eval:score -- --strict` — pass ≥ 7/10, выдумано 0,
   среднее шагов ≤ 6.

## Правило разбора

Провал сначала объясняется дефектом правил/инструмента (нет цитаты — нечем
проверить; нет доступа — не тот инструмент) и только потом слабостью модели.
Веса и «обучение» не трогаются, пока не исправлены правила.

## Запреты

- Не записывать pass без проверки цитаты руками.
- Не менять `evals/tasks.json` под результат прогона: задача — измеритель.
- Не сравнивать прогоны разных версий задач.
