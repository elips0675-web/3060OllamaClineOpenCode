## 1. Главный вывод

«Умный агент» на 3060 — это не выбор одного харнесса и не fine-tune, а четыре
слоя:

| Слой | Что это | Состояние |
|---|---|---|
| 1. Инструменты | файлы, поиск, терминал, git, БД, HTTP | есть в Cline/OpenCode, но не настроено под SQL и не проверено на 14B |
| 2. Модель | локальная 14B или облако | узкое место: одна правка в одном файле — уверенно, многофайловые задачи и нативные `tool_calls` — плохо |
| 3. Контекст | правила, примеры, память, сжатие | закрыт лучше всего |
| 4. Проверка | тесты, линт, `git diff`, эвалы | закрыт частично |

Установка OpenClose или Hermes не делает 14B умнее — она добавляет ещё один
слой правил и контекста. Поэтому сначала закрываются дешёвые шаги 1–4, потом
харнессы сравниваются на одних и тех же 10 задачах.

## 3. Что есть в OpenClose и Hermes, чего нет в комплекте

**OpenClose** (отдельный Python-проект, не плагин к Cline):

| Возможность | Детали |
|---|---|
| 14 инструментов | read/write/edit/multiedit, glob/grep, bash, webfetch, plan, ask_user, delegate, browser_automation_dom/vision, deliver_message |
| Агенты | `build` (полный доступ), `plan` (только чтение), субагент `delegate` |
| Контекст | автоматическое сжатие при подходе к лимиту |
| Skills | процедуры в Markdown, запускаются вручную и из cron |
| Jobs | расписание, одноразовые задачи, уведомления в Telegram/Discord |
| Права | allow / deny / ask на каждый инструмент |
| CLI | `openclose run -p "..."` |
| Данные | SQLite, без облака и телеметрии |

**Hermes Agent** (персональный агент, отдельный):

| Возможность | Детали |
|---|---|
| Память | автосоздание и самоулучшение навыков, поиск по прошлым сессиям (FTS5) |
| Исполнение | субагенты и параллельные задачи |
| Автоматизация | cron, мессенджеры (Telegram, Discord, Slack, WhatsApp, Signal) |
| Расширения | плагины и навыки, узкое ядро |
| Персона | `SOUL.md` — отвечать по весу вопроса, без воды |
| Бюджет промпта | `AGENTS.md` ≤ 12 КБ, цепочка ≤ 30 КБ |

Чего из этого нет в комплекте:

1. сжатия контекста (жёсткий лимит 6 вызовов и 12K ctx);
2. read-only агента-планировщика (read-only эвалы есть, планирования нет);
3. памяти между сессиями (шаблоны есть, автоматического recall нет);
4. навыков как процедур (workflows статические);
5. прав и песочницы на инструменты (держится на промпте);
6. субагентов в правилах и эвалах (в OpenCode есть, но не используются).

Инструменты у Cline и OpenCode уже есть — проблема не в их отсутствии, а в том,
что 14B плохо держит длинный цикл и нативные `tool_calls`.

## 4. SQL и карта инструментов

SQL — это три разные задачи:

| Задача | Статус | Комментарий |
|---|---|---|
| Чтение схемы и миграций | ✅ есть | агент читает `schema.prisma` и SQL-файлы, отвечает с `file:line` (проверяют E-03, E-09) |
| Живые запросы к MySQL | ❌ нет | ни у Cline, ни у OpenCode нет встроенного SQL-инструмента; SQL идёт через терминал (`mysql`, `npx prisma`) или MCP |
| Изменения схемы, миграции, данные | ⛔ запрещено без человека | риск-домен; локальная 14B не выполняет ALTER/DROP/UPDATE |

Предложение комплекта — свой `scripts/db-read.mjs`, а не MCP:

- только `SELECT`, `SHOW`, `DESCRIBE`, `EXPLAIN`;
- `LIMIT 100` по умолчанию, таймаут 10 секунд;
- отдельный пользователь MySQL только на чтение;
- лог запросов;
- тесты на запрет `INSERT`/`UPDATE`/`DELETE`/DDL.

Почему не MCP: меньше зависимостей, жёстче контроль, проще проверить тестами.
Запись и миграции — только облако + человек + гейты.

Карта инструментов:

| Домен | Cline | OpenCode | Комплект |
|---|---|---|---|
| Файлы, поиск | да | да | да (eval) |
| Терминал, тесты, git | да | да | нет (read-only) |
| SQL / БД | через CLI | через CLI | нет |
| HTTP / браузер | через MCP | да | нет |
| Память между сессиями | вручную | вручную | шаблоны |
| Расписание, Telegram | нет | нет | нет (OpenClose/Hermes) |

## 9. Итог: что получится на выходе

Коротко: локальный «умный» агент — да, но с оговоркой. Это не «DeepSeek на
3060», а дисциплинированный исполнитель узких задач плюс маршрут в облако для
сложного.

### 9.1 Железо и модель

Одна RTX 3060 12 ГБ держит Qwen2.5-Coder-14B в Q4_K_M целиком в видеопамяти:
~10.1 ГБ при `num_ctx 12288` (9 ГБ весов + ~1.1 ГБ KV-кэш), рядом живёт 1.5B
на автодополнение (~1 ГБ). Проверка одна: `ollama ps` = **100% GPU**. Скорость
25–35 ток/с, prefill 200–400. Появился «CPU/GPU split» — первым делом контекст
до 8192, а не модель полегче.

| Профиль | Модель | VRAM | Когда |
|---|---|---|---|
| `local` | 14B q4_K_M, ctx 12288 | ~10.1 ГБ | основная работа: одна правка в одном файле, офлайн |
| `local-q5` | 7B q5_K_M, ctx 16384 | ~6.5 ГБ | нужен запас VRAM под браузер/Docker |
| `local7` | 7B q8, ctx 16384 | ~8.1 ГБ | когда важна скорость |
| `cloud` | `gpt-oss:120b-cloud` (Cline) + облачная модель (OpenCode) | 0 ГБ | многофайловые задачи, ревью, миграции |

Переключение — `switch-ai.bat`, сразу в двух инструментах: Cline в VS Code и
OpenCode в терминале.

### 9.2 За счёт чего он «умный»

Ум здесь не из весов, а из четырёх слоёв, которые уже написаны:

1. **Задачу выбирает скрипт, а не модель.** `next-task.mjs` читает бэклог,
   отбрасывает закрытое и печатает карточку ~5 КБ: один пункт, один файл,
   гейты, готовый промпт. Модель не решает «с чего начать» — она получает
   узкий контекст. Это ровно то, чего не хватало Cline при переполнении.
2. **Маршрут local/cloud задаётся заранее.** Признаки: есть ли цитата
   `file:line`, попадает ли задача в риск-домен (деньги/Stripe, доступ и
   секреты, схема БД и миграции, деплой/инфраструктура), сколько файлов.
   Риск-домен или отсутствие цитаты → облако, иначе → 3060 по одному файлу.
   Автоперехода «упало локально — само ушло в облако» нет: маршрут печатается,
   решение принимает человек.
3. **Правила и память лежат в файлах.** `.clinerules` задаёт рамки: работа
   только из бэклога, запрет `any`, запрет `npm ci` под живым стеком, запрет
   деструктивных git-команд, эскалация после двух неудач подряд, **коммит
   делает человек, а не локальная модель**. Цикл шага: RESTATE → MAP → PLAN →
   ACT → VERIFY → REPORT, ≤2 поисков и ≤6 чтений, одна правка на шаг. Между
   сессиями — Memory Bank (`cline_docs/`): бриф, активный контекст, решения,
   команды и порты, прогресс. Плюс 7 процедур: `/brief`, `/fix`, `/test`,
   `/review`, `/refactor`, `/deep-planning`, `/eval`.
4. **Результат измеряется, а не «кажется лучше».** 10 задач с бинарным
   критерием и порог: ≥7/10, выдумано 0, среднее шагов ≤6. Read-only срез на
   живом проекте дал 7/7, 4.1 шага, ноль выдуманных путей — но это 7 задач из
   10: правку файла и `git diff` он не проверяет.

### 9.3 Как это выглядит в работе

Закрыть VS Code → `switch-ai.bat local` → открыть. Дальше:
`node scripts/next-task.mjs --local --out tmp/next-task.txt` → читается только
эта карточка → правка в одном файле → линт, типы, точечный тест, гейты из
карточки → дифф и вывод гейтов уходят человеку → коммит делает человек.
Задача с миграцией, платежами или секретами в локальный маршрут не попадёт.

### 9.4 Чего в итоге не будет

- **Автономного сеньора**, который сам читает репозиторий и делает
  многофайловый рефакторинг: контекст 12–16k, 14B честно проваливает длинные
  цепочки. Лечится маршрутом в облако, а не дообучением.
- **Cron, Telegram, браузерной автоматизации**: в комплекте этого нет;
  agentkai/Hermes для этого рассматривались, но не ставились.
- **MCP**: решение зафиксировано — вместо них свой `db-read.mjs` только на
  чтение.
- **LoRA**: отложено до момента, когда упор будет именно в формат ответа, а не
  в знания.
- Отдельный честный факт: у проверенных локальных моделей **нет нативных
  `tool_calls`** — они пишут JSON в текст ответа. Cline и OpenCode это
  переживают, самодельные харнессы нет: на этом провалился OpenClose (0 из 3
  задач без локального патча).

## 10. Как улучшить: что делать с каждым ограничением

Общий принцип один: сначала дешёвое, что не меняет модель, и только потом то,
что требует новых весов. Потолок 14B на 12 ГБ не поднимается увеличением
контекста — он поднимается уменьшением шага.

### 10.1 Многофайловый рефакторинг вместо «автономного сеньора»

**Дробить пункт бэклога по файлам.** Сейчас карточка даёт один пункт и один
файл. Многофайловый пункт надо резать на подпункты с отдельным ID (`QA-01a` —
`chats.tsx`, `QA-01b` — `useApi.ts`), каждый со своим гейтом и коммитом. Модель
никогда не видит больше одного файла, результат складывается из кирпичей.
Дешевле всего и работает уже сегодня.

**Читать диапазон, а не файл.** 12288 контекста — это ~300–400 строк кода вместе
с промптом и историей; шесть чтений «файла целиком» переполняют окно. Правило
жёстче: сначала `grep` по символу, потом чтение с `offset`/`limit` вокруг
совпадения. В карточку стоит добавить размер файла в строках, чтобы модель
видела цену чтения до открытия.

**Разделить планировщика и исполнителя.** Самое сильное из доступных улучшений.
Сейчас `/deep-planning` выполняет та же модель в той же сессии. Практичнее:
план строит облако (держит 8–10 файлов и не врёт про архитектуру), исполнение
идёт локально по шагам из `implementation_plan.md`, где каждый шаг — «файл +
точная правка + гейт». Локальной 14B не нужно понимать систему, ей нужно
выполнить шаг. Формально это тот же маршрут local/cloud, но с разделением по
фазам, а не по числу файлов.

**Добавить индекс символов.** Роль tree-sitter у Aider здесь закрывается дешёвым
скриптом `scripts/symbols.mjs`: regex-обход, список экспортов, функций и роутов
по файлам, вывод 3–5 КБ. Карта «где что лежит» без чтения кода снимает половину
поисков. Сто строк и тесты, без зависимостей.

**Один эксперимент с контекстом, с замером.** 14B q4 при `ctx 16384` займёт
~10.5 ГБ из 12 — впритык, шанс есть; проверяется только `ollama ps` и
`03-Замер-скорости.bat`. Альтернатива — 7B q5 с `ctx 32768` (~9 ГБ), но качество
ниже, и это мерится на тех же 10 задачах, а не «на ощупь».

Чего делать не стоит: заставлять одну сессию «понять весь проект». Это не вопрос
модели, это арифметика окна.

### 10.2 Cron, Telegram, браузер

**Свой минимум — первым.** Уже есть `agent-live.mjs` (пишет JSON-отчёт) и
`project-brief.mjs` (карта). Автоматизация «раз в сутки прогнать срез и
прислать отчёт в Telegram» — 30–50 строк: Планировщик Windows или `node-cron`,
чтение JSON, отправка через Bot API. Ноль зависимостей, ноль VRAM, проверяется
тестами. Для браузера: «зайти и прочитать страницу» закрывается `fetch`/
`webfetch` в скрипте; Chromium с кликами нужен только для логинов и форм.

**OpenClose.** Фичи реальны: Skills, Jobs с cron, Telegram/Discord, браузер,
права на инструменты. Но проверен: 0 из 3 задач, без локального патча вообще не
вызывает инструменты. Брать — ради cron/Skills, а не ради «ума», и держать патч
под контролем (не upstream, при обновлении ломается).

**Hermes / agentkai.** Только если автоматизация становится основной задачей, а
не побочной: там память, cron и шлюзы — философия инструмента. Для кодинга они
слабее, в комплекте не проверялись.

Жёсткое правило: **автоматизация без человека допустима только для read-only**
(срез, бриф, отчёт, поиск). Всё, что пишет в файлы, БД или git, остаётся за
человеком. Порядок: сначала AGT-02 (живой балл), потом автоматизация — иначе
автоматизируется непроверенное.

### 10.3 MCP и доступ к данным

Решение «свой `db-read.mjs` вместо MCP» остаётся, с уточнением: MCP оправдан там,
где нужен **внешний мир** — веб-поиск, GitHub, документация. Для схемы БД он не
нужен: `schema.prisma` и `mysql_schema.sql` читаются как файлы, это 90% вопросов.

`db-read.mjs` делать по пяти требованиям: только `SELECT`/`SHOW`/`DESCRIBE`/
`EXPLAIN`, `LIMIT 100` по умолчанию, таймаут 10 секунд, отдельный MySQL-пользователь
только на чтение, лог запросов и тесты на запрет `INSERT`/`UPDATE`/`DELETE`/DDL.
Ключевое: подключать как инструмент не нужно — агент вызывает его через
терминал (`node scripts/db-read.mjs "SELECT ..."`), это работает и в Cline, и в
OpenCode без MCP.

Если позже понадобится веб-поиск — один сервер, DuckDuckGo (без ключа), и только
под конкретную задачу: описания инструментов у 14B съедают тот самый контекст,
которого и так мало.

### 10.4 Формат ответа: structured output раньше LoRA

Между «правилами» и «дообучением» есть шаг, который в комплекте не используется:
**constrained decoding**. Ollama умеет `format: json` и схему ответа — это
заставляет модель отдавать строгий JSON вместо вольного текста. Для задач «верни
список находок с `file:line`» это лечит формат без часа обучения. Проверять на
E-07 (там нестабильный вердикт) и на `agent-live.mjs`.

LoRA имеет смысл строго при одном условии: провалы идут **по форме**, а не по
содержанию (модель находит места, но забывает `file:line`, добавляет болтовню,
ломает JSON). Тогда: датасет из существующих прогонов (`evals/live-*.json`
содержат реальные ответы), 200–500 примеров instruction/input/output, Unsloth в
Kaggle/Colab (runbook есть), экспорт в GGUF, возврат на 3060, **обязательно** тот
же набор 10 задач и базовая модель рядом для A/B.

Чего LoRA не сделает: не добавит знаний о репозитории и не поднимет потолок
многофайловых задач. Провалы по содержанию лечатся маршрутом в облако, а не
весами.

### 10.5 Нативных `tool_calls` нет — что делать

Факт неприятный, но не блокирующий: Cline и OpenCode сами разбирают JSON из
текста. Четыре шага по порядку:

1. **Клиентский парсер как страховка.** `_extract_text_tool_calls` уже написан
   для OpenClose — тот же подход переносится в любой свой харнесс: разобрать
   `<tool_call>` и JSON-объекты, проверить имя инструмента по белому списку,
   превратить в вызов. В `agent-live.mjs` такой fallback уже есть — поэтому он
   даёт 7/7 там, где OpenClose даёт 0/3.
2. **Не строить свой харнесс на 14B без этого.** Свои скрипты — read-only и с
   проверкой цитат; цикл «правка → гейт → правка» отдавать Cline/OpenCode.
3. **Проверить новую модель один раз, с замером.** Если появится сборка с
   настоящими `tool_calls`, картина меняется. Проверка дешёвая: запрос в
   `/api/chat` с массивом `tools` и взгляд на `message.tool_calls`. Но смена
   модели — это заново снятые эвалы, поэтому только по факту.
4. **Structured output как усилие.** Вызов инструмента по схеме даёт меньше
   мусора в тексте и стабильнее срабатывает парсер.

### 10.7 Порядок
