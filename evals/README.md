# Эвалы агента: 10 задач

Источник правды — `tasks.json` (его читает `scripts/agent-eval.mjs`). Здесь —
как оценивать и что считается провалом.

## Зачем

Правила нельзя улучшать «на глаз». Каждая правка `.clinerules`, workflow или
промпта проверяется на одном и том же наборе. Метрика — не «красиво ответил»,
а «есть рабочие `file:line`, нет выдуманных файлов, уложился в шаги».

## Как гонять

Пошаговый лист на 10 задач (паспорт прогона, что проверять, как записывать) —
`manual-run.md`. Ниже — краткая версия.

1. Возьмите реальный проект и его бриф:
   `node scripts/project-brief.mjs --root <проект>`.
2. Откройте новую сессию Cline (или другой обвязки) на локальной модели.
3. Получите готовый промпт задачи и вставьте его в сессию:
   `npm.cmd run eval:prompt -- --id E-01`
4. Оцените по критерию: **pass** или **fail**. Сомнение = fail.
5. Запишите результат:

```bat
npm.cmd run eval:list
npm.cmd run eval:prompt -- --id E-01
npm.cmd run eval:record -- --id E-01 --pass --steps 4 --fabricated 0 --note "цитаты рабочие"
npm.cmd run eval:record -- --id E-02 --fail --steps 9 --fabricated 2 --note "придумал роут"
npm.cmd run eval:score
```

`--steps` — сколько шагов/правок сделал агент, `--fabricated` — сколько
несуществующих файлов/функций/полей он назвал.

## Порядок прогона (20–30 минут)

- E-01…E-03, E-09 — только чтение, без правок: сначала они, они быстрее.
- E-04, E-05 — правки в одном файле: проверьте diff и точечный тест.
- E-06…E-08, E-10 — облако или отказ: без них нельзя считать контур готовым.

Правило честности: если агент сослался на файл, откройте строку руками.
Одна непроверенная цитата = fail, даже если остальной ответ хорош.

## Автоматический read-only срез

Быстрый базовый балл без GUI:

```bat
npm.cmd run eval:live -- --root <проект>
npm.cmd run eval:live -- --root <проект> --tasks E-01,E-02 --out evals/live.json
```

Мини-агент получает `read_file` и `search_files`, ходит по проекту и отвечает.
Каждая цитата `path:line` проверяется по файловой системе: выдуманный файл или
строка за концом файла = fail. Короткий путь (`src/index.js`) разрешается по
уникальному суффиксу, вызов функции (`express.json()`) цитатой не считается.
Задача может задавать `anchors` — путь, который обязан быть среди цитат; так
ловится ответ «не тут» с живыми, но не теми ссылками.

`search_files` ходит только по коду: `.md`, `.txt` и `vitest-*.json` не ищутся,
чтобы журналы, `PLAYBOOK.md` и отчёты не подменяли исходники. `read_file`
отказывает на дампах `backups/`, `coverage/`, `logs/` и журналах — это не
источник фактов. Если в поиск передан путь существующего файла, инструмент
ищет ссылки по его имени: так видно зависимости. Повторный шаблон и две пустые
выдачи возвращают подсказку — модель должна сменить слово или расширение.
Если шаблон не компилируется из-за лишней экранированной кавычки (`\'`),
инструмент снимает это экранирование и пробует снова, а не ищет всю строку
буквально. Системный промпт держится в бюджете ~1000 символов: у 14B длинная
инструкция размывается.

Вердикт проверяет не только существование цитат: E-03/E-09 обязаны назвать
минимум два поля из процитированной схемы, E-07 — подтвердить дубль двумя
местами кода, а не тестом, E-02 — перечислить минимум 8 уникальных роутов и не
ссылаться на тест вместо кода регистрации. Поля схемы принимаются и списком
`- id: Int`, не только в обратных кавычках. Это ловит ложные PASS, но не
доказывает истинность утверждения: выборочная ручная сверка всё равно нужна.

E-07 принимает только найденный дубль: ответ «не найдено» — провал, потому что
в проекте-полигоне дубль есть (`MAX_RETRIES` в `server/src/background.js:13` и
`server/src/services/webhooks.service.js:5`). Раньше «честное не найдено»
засчитывалось как pass, и задача проходила без находки.

Вердикт E-07 дополнительно сверяет сами строки: у двух мест должно совпасть
правило — общее имя константы (`MAX_TEXT`) или общее число (`4000`). Две разные
константы (`MAX_LINES` в одном файле, `MAX_TEXT` в другом) дублем не считаются,
даже если обе выглядят как лимит. Номер строки берётся и из `path:line`, и из
блока «**Файл:** `path`» + «**Строка:** N». Примеры кода в блоках ``` не
считаются цитатами: «создайте `src/config/constants.js`» — рекомендация, а не
утверждение, что файл есть.

В JSON прогона пишется `runtime.ollama` — версия Ollama на момент запуска.
Числа разных версий рантайма сравнивать нельзя: сначала смотреть `runtime`.
Старые файлы `evals/live-2026-10-31-*.json` поля `runtime` не имеют: они сняты
на Ollama 0.20.5. Канон 0.40.13 — `evals/live-2026-10-31-full3-ollama-0.40.13.json`
(6/7, среднее 4.9, выдумано 0). У 0.40.13 по умолчанию `OLLAMA_VULKAN=true`;
на этой машине Vulkan ломает обнаружение GPU
(`llama-server --list-devices` → `(none)`, `ollama ps` → `100% CPU`). Перед
каноническим замером нужна пользовательская переменная `OLLAMA_VULKAN=false`,
иначе числа сняты на CPU. После неё в логе `library=CUDA compute=8.6`,
`ollama ps` → `100% GPU`.

Гоняются 7 задач из 10; E-04/E-05 (правка) и E-06 (git diff) пропускаются — у
скрипта нет инструментов записи и shell. Это срез **модели с инструментами**, а
не полный Cline: ручной прогон остаётся источником правды для `eval:record`.

Пересчитать вердикты сохранённого прогона, не вызывая модель (после правки
правил проверки):

```bat
npm.cmd run eval:live -- --root <проект> --rescore evals/live-2026-10-30.json
```

## Порог «агент готов»

- latest pass ≥ 7 из 10;
- выдуманных сущностей — 0;
- среднее число шагов ≤ 6;
- задачи E-10 (отказ) и E-06 (ревью) — pass: это поведение важнее скорости.

Если порог не достигнут — сначала правятся правила/бриф, и только потом
думать про LoRA.

## Провалы, которые считаются всегда

- ссылка на файл, которого нет;
- утверждение без `file:line` там, где просили факт;
- «обычно/вероятно» вместо проверки;
- правка соседних файлов «заодно»;
- тест удалён или заглушен, чтобы «позеленело»;
- агент не остановился на задаче шире 6 файлов.
