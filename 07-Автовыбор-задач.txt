1. ЗАЧЕМ ЭТО
================================================================================

Локальная модель 14B не может сама выбрать задачу: «Что доделать.txt» — около
18 тыс. токенов, а контекст 12288. Плюс выбор «на глаз» каждый раз разный.

Поэтому выбор делает скрипт (детерминированно, офлайн), а модель только
исполняет одну узкую карточку. Один и тот же файл бэклога всегда даёт одну и ту
же задачу — это проверяемо и повторяемо.

Файл скрипта: scripts/next-task.mjs
Тест:         scripts/next-task.test.mjs (46 тестов, зелёные)
Команда:      npm.cmd run task:next

================================================================================
2. ЧТО ЧИТАЕТ СКРИПТ
================================================================================

Источник правды — только «Что доделать.txt» в корне проекта. Ничего не
выдумывается: нет пункта в файле — нет задачи.

Разбор:
  • разделы P0–P3, «Ждёт действий пользователя», «Очередь этапов» — берутся;
  • «Принятые решения», «Не брать», «Правила работы» — пропускаются целиком;
  • пункт без ID вида QA-01/P2-03 — не задача, игнорируется.

Статусы (главное отличие от первой версии):

  ready       — брать можно
  blocked     — заблокирована владельцем: ключи, домен, staging, юридический
                текст, «решение владельца», ENV-*/AND-*/CI-*/LEGAL-*
  closed      — уже сделана («закрыт Stage 162» и подобное)
  decision    — принятое решение, а не работа («риск принят», «осознанное
                ограничение»)
  no-evidence — нет ни одного `файл:строка` / `файл` в тексте пункта

Правила выбора:
  • closed и decision не выдаются никогда, даже через --id;
  • blocked — только с явным --include-blocked;
  • no-evidence — только с --allow-no-evidence;
  • один и тот же ID, встреченный дважды, схлопывается в одно вхождение,
    приоритет у того, где есть `file:line` (в бэклоге есть повторы).

3. КОМАНДЫ
================================================================================

  npm.cmd run task:next
      Карточка следующей задачи (по умолчанию — по порядку приоритетов P2 → P3).

  npm.cmd run task:next -- --local
      То же, но только пункты, которые скрипт сам отправляет на 3060: точная
      цитата `file:line` и ни одного «риск-домена» (см. ниже). Число файлов при
      этом не ограничивается: карточка режет пункт по одному файлу за подход и
      пишет это в строке «Маршрут».

  npm.cmd run task:next -- --route
      Только решение о маршруте, одна строка: `local` или `cloud` + причина.
      Карточку не печатает. Удобно, когда нужно скормить решение скрипту или
      посмотреть, куда уйдёт текущая задача, до запуска модели.

  Маршрут (routeFor) решает по трём признакам, в этом порядке:
      1) нет цитаты `file:line`          -> cloud (правило проекта);
      2) текст пункта или путь файла попал в риск-домен -> cloud;
      3) иначе                          -> local, по одному файлу за подход.
      Риск-домены (там 14B ошибается молча, а ошибка стоит денег или доступа):
      деньги (Stripe, подписка, оплата, возврат, выплата, комиссия),
      доступ (JWT, OAuth, auth, CSRF, adminAuth, секрет, токен, уязвимость,
      IDOR, rate-limit, пароль, sanitiz, XSS, SQL-инъекция),
      схема БД (миграция, mysql_schema, ALTER/CREATE TABLE, ENUM, CHECK,
      schema, индекс),
      инфраструктура (docker, compose, deploy.yml, nginx, деплой, kubernetes).
      Это ключевые слова, а не оценка сложности: тяжёлую, но «тихую» задачу
      скрипт может отправить локально — глазами всё равно смотреть человеку.

  npm.cmd run task:next -- --list
      Таблица всех пунктов: ID, приоритет, строка в бэклоге, статус, цитата,
      число файлов, признак «из очереди этапов», название. Ничего не выбирает.

  npm.cmd run task:next -- --id QA-01
      Конкретный пункт. Если он закрыт/решение — откажет и скажет причину.

  npm.cmd run task:next -- --queue-only
      Только раздел «Очередь этапов» (сейчас там 3 пункта, из них 2 блокера).

  npm.cmd run task:next -- --json            карточка в JSON (для скриптов)
  npm.cmd run task:next -- --out tmp/next-task.txt   сохранить в файл
  npm.cmd run task:next -- --include-blocked --allow-no-evidence
                                             показать всё, включая блокеры

Коды выхода: 0 — задача найдена, 1 — брать нечего, 2 — ошибка аргументов
или чтения (нет файла бэклога, файл заблокирован).

ВАЖНО (Windows): в PowerShell пишите `npm.cmd`, а не `npm` (политика
исполнения блокирует npm.ps1). Ещё вариант — запускать из cmd.

================================================================================
5. КАК ЭТО ВСТРАИВАЕТСЯ В РАБОТУ
================================================================================

Полный цикл одного блока (5 шагов, ничего не выдумано — это правила проекта):

  1. npm.cmd run stage:context       — где мы: git, последний Stage, счётчики,
                                       открытые пункты очереди, гейты
  2. npm.cmd run stage:preflight     — всё ли зелёное ДО начала (tsc, eslint,
                                       счётчики, check:docs/mirrors/env-parity,
                                       окно 6 файлов / 300 строк)
  3. npm.cmd run task:next -- --local   — ОДНА задача и готовая карточка
  4. агент (Cline локально / OpenCode облако) исполняет карточку
     -> гейты из карточки, все должны быть exit 0
  5. npm.cmd run stage:checkpoint    — запись Stage N.Y в журнал, коммит
                                       поимённо, push; на красном окне не
                                       трогает ничего

Коммит и push на шаге 5 делает человек. Локальная модель (14B) не выполняет
git add / commit / push: она показывает дифф, гейты и список файлов, а решение
о коммите остаётся за владельцем (правило .clinerules 11.1). Скрипт
stage:checkpoint от этого не меняется — его просто запускает человек.

Пункты 1, 2, 5 — уже готовые скрипты проекта, я их не менял. Новое только 3.

Как отдать карточку агенту:
  • Cline: скопировать блок «ПРОМПТ ДЛЯ АГЕНТА» целиком в чат.
  • OpenCode: `opencode run "<вставить промпт>"` из корня проекта.
  • Файл: `npm.cmd run task:next -- --out tmp/next-task.txt`, затем открыть
    tmp/next-task.txt (каталог добавлен в .gitignore, в коммит не попадёт).

Чего в карточке нет намеренно:
  • нет «сделай хорошо» — только текст пункта и один файл;
  • нет права менять другие файлы без разрешения;
  • нет разрешения на any / as any / @ts-ignore;
  • нет автокоммита — коммит только через stage:checkpoint, после зелёных гейтов.

6. ЧЕСТНЫЕ ОГРАНИЧЕНИЯ
================================================================================

1. Скрипт выбирает, но не проверяет качество работы. «Зелёный eslint» на any не
   значит «типы правильные»: замена any на unknown проходит линт и меняет смысл.
   QA-01 всё равно смотрят глазами — по одному файлу.

2. Полный автопилот не сделан осознанно. Причина: из трёх пунктов очереди два —
   блокеры владельца, третий — многочасовая работа с циклом «тест → прогон →
   фикс». Автоцикл упрётся в лимит итераций на первом же файле, а «зелёные
   гейты» не доказывают корректность.

3. Пункты без цитаты кода (P2-01..P3-08, STORY-01, TEST-04) не выдаются: правило
   проекта — пункт без `file:line` не принимается. Это не баг скрипта.

4. Голое имя файла (`admin-queues.test.js` без каталога) достраивается по
   репозиторию, только если совпадение единственное. Если таких файлов два —
   путь остаётся как в бэклоге, и это видно в карточке.

5. Скрипт не меняет «Что доделать.txt». Закрытие пункта — ручная правка или
   stage:checkpoint, как и раньше.

6. Тесты скрипта лежат в scripts/ и не попадают в счётчики инвентаря
   (test-counter-audit считает только src/ и server/), поэтому гейт счётчиков
   они не сдвигают.

7. Маршрут «локально / облако» — это правило по ключевым словам, а не оценка
   сложности. Скрипт не читает код и не знает, сколько времени займёт правка.
   Ложное срабатывание в обе стороны возможно: «токен» в тексте задачи отправит
   её в облако, а тяжёлый рефакторинг без таких слов останется локальным.
   Поэтому строка «Маршрут» — совет, последнее слово за человеком.

8. Смена маршрута не переключает модель сама. Скрипт только печатает решение;
   запуск `opencode run` с моделью (локальной или облачной) делает человек или
   команда `/next` / `/next-cloud`. Автоматического «упало локально — ушло в
   облако» нет и не планируется.
